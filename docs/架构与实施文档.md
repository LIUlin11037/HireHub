# HireHub 架构与实施文档

> 招聘 / 求职平台 · Java 微服务实习简历项目
> 版本：v1.0（选型冻结稿） · 基础包名：`com.ll.hirehub`

## 0. 文档说明

本文档是**选型冻结后的实施方案**，只定义架构，不含业务代码。目标是把"服务边界、数据模型、核心链路、技术决策"先定下来，避免边写边改导致返工。

> 各关键决策的**背景、备选方案与取舍理由**单独记录在 `docs/关键决策记录.md`（ADR 格式），本文档只呈现结论。

本版已落地决策：

| 决策 | 结论 |
|---|---|
| 分布式事务 | **移除 Seata**，改用**本地消息表 + MQ 最终一致性** |
| 认证鉴权 | **Spring Security 6 + JWT**（Boot 3 写法） |
| 缺失组件 | 补齐 **MinIO / 接口文档 / 链路追踪 / 延迟消息** |
| 身份模型 | 账号 + 全局角色 + **企业维度角色**；新增 `PLATFORM_ADMIN` 管理端（见 §5.2 / §6.1） |

## 1. 项目定位与简历目标

### 1.1 目标

实习简历项目的评价标准不是"用了多少组件"，而是**"你能把一个技术决策讲多深"**。因此本项目的核心原则是：

- **组件数量做减法，链路深度做加法**：宁可 8 个组件讲透，不要 15 个组件只会调 API。
- **每个技术选择都要有"为什么"和"为什么不选另一个"**。
- **不编造压测数据**。可以写"本地压测下单机约 XXX QPS"，但必须是自己真跑出来的，面试官会追问环境和方法。

### 1.2 反目标（明确不做）

- ❌ 不做分库分表（ShardingSphere）—— 项目数据量撑不起，硬上会被问穿
- ❌ 不做支付 / 订单体系 —— 会显著扩大范围，第一期不做
- ❌ 不做 WebRTC 实时音视频 —— 成本极高，见 §11.3
- ❌ 不追求服务数量 —— 服务拆得多不等于架构好
- ❌ 不做企业库预置（不从工商数据批量收录企业）—— 工商数据不含求职者关心的信息，未经企业确认的展示有合规与责任风险（见 D-20）

### 2.2 新版路线专项踩坑清单 ⚠️

这条路线版本很新，以下几个坑**必须提前知道**，否则会在环境上卡住：

#### ① Gateway 坐标改名（Spring Cloud 2025.0.0 破坏性变更）

```
旧：org.springframework.cloud:spring-cloud-starter-gateway
新：org.springframework.cloud:spring-cloud-starter-gateway-server-webflux
```

旧坐标已废弃。网上 90% 的 Gateway 教程用的是旧坐标，直接抄会引入不到依赖或报错。同时**配置属性前缀也有迁移**，别照搬旧教程的 yml。

#### ② Nacos 3.0 端口拆分

| 端口 | 用途 |
|---|---|
| 8848 | HTTP API（AdminAPI / OpenAPI） |
| 9848 | 客户端 gRPC（**必须放行**） |
| 9849 | 服务端间 gRPC |
| 7848 | Jraft |
| **8080** | **控制台 + 控制台 API（独立端口）** |

Nacos 3.0 把**控制台从主端口剥离了**。所以：
- 控制台地址是 `http://localhost:8080`，**不是** `http://localhost:8848/nacos`
- 项目里网关等服务的 HTTP 端口**不能再占用 8080**

#### ③ MyBatis-Plus 3.5.9+ 分页插件依赖拆分

自 3.5.9 起，插件部分（依赖 jsqlparser）改为**可选依赖**。想用**分页插件**必须额外引入：

```xml
<dependency>
  <groupId>com.baomidou</groupId>
  <artifactId>mybatis-plus-jsqlparser</artifactId>
</dependency>
```

不引入的话，分页插件直接 Bean 创建失败。建议引入 `mybatis-plus-bom` 统一版本。

另外：**引入 MyBatis-Plus 后不要再引 `mybatis-spring-boot-starter`**，会冲突。

#### ④ springdoc-openapi 只能用 2.x

- `springdoc-openapi 2.9.1` → **Spring Boot 3.x**（本项目用这个）
- `springdoc-openapi 3.x` → Spring Boot 4.x（**不要用**）

**Knife4j 的风险**：Knife4j 最新正式版为 `4.5.0`（2024-01），其内部绑定的 springdoc 版本较旧，与 Boot 3.5 存在已知适配摩擦。

> **建议**：一期**先用原生 springdoc-openapi 2.9.1 + Swagger UI**（零风险，够用）。
> 想要 Knife4j 的增强 UI，二期再评估，届时需排除其传递的 springdoc 并显式覆盖到 2.9.1。

#### ⑤ 命名空间变更

Boot 3 全线 `javax.*` → `jakarta.*`。任何 Boot 2 时代的教程（Security 配置、Servlet API、校验注解）都不能直接抄。

## 5. 数据库设计

### 5.1 库划分

**每服务独立 schema，禁止跨库 JOIN**（跨服务数据用 Feign 或冗余字段）。

| 库名 | 归属服务 | 核心表 |
|---|---|---|
| `hirehub_auth` | auth | `sys_user`, `sys_role`, `sys_user_role`, `sys_operation_log` |
| `hirehub_company` | company | `company`, `company_member`, `company_verify_record` |
| `hirehub_job` | job | `job`, `job_category`, `job_stat` |
| `hirehub_resume` | resume | `resume`, `resume_attachment`, `resume_education`, `resume_experience`, `job_preference`, `push_record` |
| `hirehub_delivery` | delivery | `delivery`, `local_message`, `mq_consume_log` |
| `hirehub_interview` | interview | `interview`, `interview_feedback` |
| `hirehub_notification` | notification | `notification`, `notification_receiver` |

### 5.2 核心表（关键字段）

> 通用字段：`id BIGINT PK`, `create_time`, `update_time`, `deleted TINYINT`（逻辑删除）

#### 身份模型（重要）⚠️

**这套模型是「1 个账号 + 2 个维度的角色 + 3 种推导出来的身份」，不是分层的。**

```
账号（sys_user）
  │
  ├── 全局角色（auth 服务）        SEEKER / PLATFORM_ADMIN
  │
  └── 企业维度角色（company 服务）  OWNER / HR      ← 挂在 company_member 上

三种身份（推导，不落库）：
  求职者  = 拥有 SEEKER 全局角色
  雇佣者  = 有正常的 company_member 记录
  管理员  = 拥有 PLATFORM_ADMIN 全局角色
```

⚠️ 注意区分：**`sys_user` 上没有任何区分求职 / 招人的字段**。区分靠的是「全局角色」和「企业成员关系」两处——这正是下面表格里三个身份不在同一维度的原因。

| 身份 | 判定方式 | 归属维度 |
|---|---|---|
| 求职者 | 拥有 `SEEKER` 全局角色 | 平台全局 |
| 雇佣者 | 存在一条 `status=正常` 的 `company_member` 记录 | **企业维度** |
| 管理员 | 拥有 `PLATFORM_ADMIN` 全局角色 | 平台内部 |

单值 `user_type` 会锁死两个真实场景：
① 一个人**既是求职者又是 HR**（HR 自己也找工作，很常见）；
② 一个人在**多家公司任职**（A 公司 HR + B 公司 Owner）。

**`sys_user`** ← 账号（自然人），**不含任何身份字段**；实名信息属于"人"的维度
```
id, username(uk), password(BCrypt), phone(uk), email, nickname, avatar,
status, last_login_time,
real_name(加密), id_card_no(加密), real_name_status(未认证/已认证/驳回), real_name_time
```
> ⚠️ `id_card_no` 属敏感个人信息，**必须加密存储 + 日志脱敏**（见 D-16 / D-18）

**`sys_role`** ← 全局角色字典
```
id, code(uk: SEEKER / PLATFORM_ADMIN), name, description
```

**`sys_user_role`** ← 账号 ↔ 全局角色（一个账号可多角色）
```
id, user_id, role_id
uk (user_id, role_id)
```

**`sys_operation_log`** ← 管理员操作审计（回应"管理员误操作怎么追溯"）
```
id, operator_id, operator_name, module, action, target_type, target_id,
before_value(JSON), after_value(JSON), ip, create_time
idx (operator_id, create_time), idx (target_type, target_id)
```

**`company`**
```
id, name, credit_code(uk：统一社会信用代码) ← 企业唯一标识，不能用名称,
legal_person_name(工商返回的法人姓名), business_status(存续/注销/吊销),
logo_url, industry, scale, city, address, description,
verify_status(待审核/通过/驳回/已撤销), verify_time, verify_remark,
invite_code(企业邀请码), invite_code_expire_time(邀请码有效期)
```
> ⚠️ **唯一标识用统一社会信用代码，不用企业名称**——企业会改名，且相似名称极多
> （"XX科技有限公司" vs "XX网络科技有限公司"），用名称判重会导致同一家公司重复注册（见 D-18）。
>
> **不设 `owner_id`**：OWNER 的唯一数据源是 `company_member.role = 'OWNER'`，避免双数据源不一致（见 D-17）。
>
> **企业记录随入驻产生，平台不预置**：不建企业库、不从工商数据批量收录（见 D-20）。
> 因此平台上不存在"没有招聘者的企业"，`company` 表纯粹表达「入驻企业」这一概念。

**`company_member`** ← **「雇佣者」身份的真实载体**，也是企业维度隔离的关键
```
id, company_id(索引), user_id, role(OWNER/HR),
is_legal_rep(标记：实名姓名与企业法人一致，**非权限开关**),
status(正常/离职), join_time
uk (company_id, user_id)
```
> 一个人可在多家公司拥有不同角色；`status=正常` 才代表当前具备"雇佣者"身份。
> 该记录置为离职后，雇佣者身份自动消失——**不需要回去改账号表**。
> 加入方式：**凭企业邀请码直接加入**（见 D-19），不做 OWNER 审批。
> OWNER 缺失时由平台管理员人工介入（见 D-17）。
>
> ⚠️ **角色只有 `OWNER` / `HR` 两个**。不设 `INTERVIEWER`：面试官是**按面试实例**授权的，
> 不是企业成员的固定属性（否则同一个人跨岗位无法区分）。本期更进一步简化为**由 HR 代录面试反馈**，
> 面试官姓名以文本记录在 `interview.interviewer_name`。

**`company_verify_record`** ← 企业认证留档（**有法律后果的操作，必须可追溯**）
```
id, company_id(索引), submitter_id, credit_code, company_name,
legal_person_name, license_url, verify_channel(MOCK/ALIYUN),
request_snapshot(JSON：提交材料), response_snapshot(JSON：第三方返回原文),
result(通过/驳回), remark, operator_id, create_time
idx (company_id, create_time)
```

**`company_authorization`** ← 法人授权令牌（见 D-24 第三层）
```
id, company_id, credit_code, legal_person_name,
applicant_id,                         -- 申请人
authorization_token(uk), token_expire_time,
status(待授权/已授权/已过期/已拒绝/已撤销),
legal_person_user_id,                 -- 法人实名后落到的账号（可空）
authorized_time, create_time
idx (company_id, status)
```
> 法人**无需注册账号**，通过一次性授权链接完成实名 + 确认（见 §6.7）。

**`job_category`** ← 职位分类树（模仿 BOSS 划分，**两级足够**）
```
id, parent_id(一级为 0), name, level(1/2), sort, status
idx (parent_id, sort)
```
> 一级类目（技术 / 产品 / 设计 / 运营 / 市场 / 销售 / 职能 / 金融 …）
> → 二级职位（后端开发 / 前端开发 / 算法 / 测试 / 运维 …）
>
> 更细的技能词（Java / Go / Python）交给**搜索关键词与职位标签**，**不做第三层**。
> 分类用于 ES 的 **filter + 聚合**（前端筛选器、各类目职位数），与关键词全文检索**互补**。

**`job`** ← 职位主体（**公司名不存这里**，只存 `company_id`）
```
【归属】      id, company_id(索引), publisher_id(发布者，仅留痕，不作权限边界)
【标题/分类】 title, category_id, skills(JSON：["Java","Spring Boot","MySQL"])
【地点】      city, district(区/商圈), address(详细地址), remote(是否远程)
【薪资】      salary_min, salary_max, salary_type(月薪/年薪), negotiable(是否面议)
【人才要求】  education(不限/大专/本科/硕士/博士), experience(不限/1-3年/3-5年/5-10年),
              headcount(招聘人数), job_type(全职/兼职/实习)
【富文本】    description(职位描述), requirement(任职要求)
【状态】      status(草稿/招聘中/已下线/已满),
              offline_reason(手动/企业认证失效/管理员下架/已招满/已过期),
              publish_time, expire_time
【统计】      delivery_count(投递数), view_count(浏览数)  ← 高频更新，细粒度统计拆到 job_stat
```

> **公司名为什么不在 job 表**：只存 `company_id`，避免公司改名时全表同步。
> 搜索/展示层在 `job_index` 里**冗余** `company_name`（反规范化，列表页零 join）。
>
> **不设性别 / 年龄字段** ⚠️：招聘信息写「限男性 / 35 岁以下」属就业歧视（《就业促进法》），
> 从 schema 层面直接杜绝，运营想填都填不了。

## 6. 核心链路设计

### 6.1 认证鉴权链路

**身份模型**：账号（`sys_user`）+ 全局角色（`SEEKER` / `PLATFORM_ADMIN`）+ 企业维度角色（`company_member.role`）。
「雇佣者」不是账号上的字段，而是"拥有至少一条正常的 `company_member` 记录"。详见 §5.2。

```
登录 → auth 服务校验密码
     → 签发 accessToken(30min) + refreshToken(7d)
     → accessToken 携带：userId、全局角色 roles、jti
                              ↓
                   refreshToken 存 Redis: refresh:{userId}:{jti}（可主动撤销）
                              ↓
请求 → 网关校验签名 + 有效期 + 黑名单
     → 解析出 userId / roles / jti
     → 写入请求头 X-User-Id / X-User-Roles / X-Company-Id（如有）
     → 转发下游（下游信任内网，不再解析 JWT）
     → 下游服务【手工构建 SecurityContext】← 否则 @PreAuthorize 拿不到身份
```

关键设计点：

1. **无状态 + 可控撤销**：accessToken 无状态便于校验；refreshToken 存 Redis 支持登出/改密后失效。
2. **登出**：把 accessToken 的 `jti` 写入 Redis 黑名单，TTL = 该 token 剩余有效期。
3. **双 token**：accessToken 短期降低泄露风险；refreshToken 长期换新，避免频繁登录。
4. **网关统一鉴权**：下游服务不重复解析 JWT，减少耦合；内部服务间调用靠内网 + 请求头传递身份。
5. **⚠️ 下游必须手工构建 `SecurityContext`**：网关鉴权模式下下游不再解析 JWT，需要用透传的请求头构造认证对象写入 `SecurityContextHolder`。
   这是"网关鉴权 + 方法级鉴权"最容易漏的衔接点——漏了会导致 `@PreAuthorize` 全部拒绝或全部放行。
6. **全局角色进 token，企业角色不进 token**：企业成员关系会变。若把 `company_member.role` 写进 token，HR 被移除后 token 里仍是 HR，最长 30 分钟才失效。
   → 企业维度权限**每次请求实时判定**（走 Redis 缓存），或在成员变更时主动吊销该用户 token。
7. **越权防护**（面试高频，比 JWT 本身更值钱）：
   - **水平越权**：改 URL 里的 `resumeId`/`deliveryId` 访问他人数据 → 所有查询**强制拼接 `user_id` / `company_id` 条件**，不信任前端传参
   - **垂直越权**：普通用户调管理接口 → Spring Security `@PreAuthorize` 方法级鉴权
   - **注册提权** ⚠️：`POST /register` **硬编码只创建 `SEEKER`，忽略客户端传入的任何角色字段**；`PLATFORM_ADMIN` 只能由数据库初始化脚本产生
   - **企业数据隔离**：HR 只能看本企业数据 → 统一从 `X-Company-Id` 取，配合 MyBatis-Plus 多租户插件

#### 身份切换（无状态设计）⚠️

「求职者 / 雇佣方」的切换**不做服务端状态**，也不提供 `POST /switch-identity`（决策依据见 `docs/关键决策记录.md` D-06）。理由：

1. **API 层面无歧义**：`/delivery/mine` 是求职者行为、`/delivery/received` 是 HR 行为，接口语义本身已表达身份
2. **有状态会多端互相覆盖**：手机切 HR、电脑切求职者，服务端单值状态互踩，并退回 session 模式
3. **切换接口是新的提权面**：典型漏洞是只校验"有 `company_member` 记录"却未校验 `companyId` 归属

**做法**：

```
GET /api/auth/me/identities     # 只读查询可用身份，供前端渲染切换器
                                # ⚠️ auth 只返回【全局角色】；「所属企业列表」由前端另调 company 获取
                                #    auth 不做 Feign 聚合 —— 避免 auth 依赖 company，
                                #    且 company 故障不影响登录后的基础页面
前端切换 = 只改路由与请求头，不调后端
身份体现在 URL 路由（/seeker/** vs /recruiter/**），而非"当前身份"变量
企业上下文用 X-Company-Id，后端每次校验归属，缓存 Redis，成员变更时失效
```

### 6.2 投递：状态机 + 最终一致性 ★核心亮点

#### 投递状态机（事件驱动）

**8 个状态**，终态 3 个（`HIRED` / `REJECTED` / `CANCELLED`）：

```
PENDING → VIEWED → COMMUNICATING → INTERVIEW → OFFER → HIRED
   │         │           │              │          │
   │         │           │              │          └─ HR 撤回 → REJECTED
   │         │           │              └─ 求职者拒 Offer → CANCELLED
   │         │           └─ 放弃 → CANCELLED / 不合适 → REJECTED
   │         └─ 放弃 → CANCELLED
   └─ 撤销投递 → CANCELLED
```

**迁移矩阵（合法迁移白名单）**：

| 从 | 到 | 事件 | 发起方 |
|---|---|---|---|
| PENDING | VIEWED | 查看 | 系统（HR 打开详情自动） |
| PENDING | COMMUNICATING | 发起沟通 | HR（隐含已查看） |
| PENDING | INTERVIEW | 约面试 | HR（**可跳过沟通**） |
| PENDING | CANCELLED | 撤销投递 | 求职者 |
| VIEWED | COMMUNICATING / INTERVIEW | 沟通 / 约面 | HR |
| VIEWED | CANCELLED | 撤销 | 求职者 |
| COMMUNICATING | INTERVIEW / REJECTED | 约面 / 不合适 | HR |
| COMMUNICATING | CANCELLED | 放弃 | 求职者 |
| INTERVIEW | OFFER / REJECTED | 面试通过 / 不合适 | HR |
| INTERVIEW | CANCELLED | 放弃 | 求职者 |
| OFFER | HIRED / REJECTED | 确认入职 / 撤回 | HR |
| OFFER | CANCELLED | 拒绝 Offer | 求职者 |
| 任何终态 | 任何 | — | ❌ |

**职责边界**：`REJECTED` = **HR 终止**（不合适 / 面试不过 / 撤回）；`CANCELLED` = **求职者终止**（撤销 / 放弃 / 拒 Offer）。

**防 if/else 泥潭的三个原则**：

1. **事件驱动，不是目标状态驱动**——HR 发起 `SEND_OFFER` 事件，状态机查表决定能否迁移，而不是"把状态改成 OFFER"
2. **迁移表驱动**——合法迁移存进 `Map<Status, Set<Event>>`，迁移 = 查表，新增迁移只加一行，不碰判断代码
3. **权限绑定在事件上**——`CANCEL` 只能求职者本人发起，`REJECT / SEND_OFFER / HIRE` 只能 HR

```java
void transition(delivery, event, actor) {
    1. 校验事件在该状态下合法       // 查 transitions
    2. 校验 actor 有权限发起该事件   // 查 actorRules
    3. 乐观锁执行 UPDATE ... WHERE status = 前态
}
```

**并发**：`UPDATE delivery SET status='INTERVIEW' WHERE id=? AND status='COMMUNICATING'`，affected rows = 0 即迁移失败（别人已改）。

**为什么不用 Spring Statemachine**：太重；自建「枚举 + 迁移表 + transition 方法」即可，且能讲清原理（不是框架黑盒）。

**API 边界（关键）**：

- 前端**只发事件、不传目标状态**；`status` 对前端只读，只能由状态机根据事件派生
- `VIEW` 事件**不由前端显式发**：HR 调用 `GET /deliveries/{id}` 打开详情时，系统自动 `PENDING → VIEWED`（否则前端会漏发、且语义重复）
- 事件接口：`POST /deliveries/{id}/events { type: "CONTACT" | "INVITE_INTERVIEW" | ... }`
- 非法迁移（如 `PENDING + SEND_OFFER`）在查表阶段返回 400——前端**不可能把状态"设错"**，越权与跳步在 API 层就被堵死

#### 最终一致性（跨服务副作用）

**问题**：一次投递要跨三个服务：

```
delivery 写投递记录  →  job 投递数 +1  →  notification 通知 HR
```

**为什么不用 Seata**：投递是高频写，Seata AT 的全局锁 + `undo_log` 开销不划算；且"通知失败"本来就不该回滚整笔投递——用户投递成功了，通知没发出去应该重试而不是撤销。投递计数短暂不准也不影响正确性。所以选**最终一致性**。

**方案：本地消息表**

```
① 本地事务（同库同事务，保证原子性）
   INSERT delivery (...)
   INSERT delivery_resume (delivery_id, resume_id, resume_snapshot)   ← 简历快照
   INSERT local_message (status=0, next_retry_time=now, payload=JSON)
   COMMIT

② 定时任务（每 5s，分布式锁防并发）
   SELECT * FROM local_message
    WHERE status=0 AND next_retry_time <= now LIMIT 100
   → 投递到 RabbitMQ（开启 publisher confirm）
   → 成功：status=1；失败：retry_count++, 指数退避 next_retry_time

③ 消费者（job / notification 服务）
   手动 ACK + 幂等去重（mq_consume_log 唯一索引 或 Redis SETNX）
   → 业务处理 → 写 mq_consume_log → ACK

④ 状态回写
   消费者处理成功 → 回写 local_message.status=2
   （或由消费者发一条 ACK 消息，delivery 消费后更新）

⑤ 对账补偿任务（每小时）
   扫描 status=1 且超过阈值仍未确认的记录 → 重新投递
   扫描 retry_count > 5 的记录 → status=3 + 告警
```

**为什么这样设计**：
- ① 保证"业务成功 ⟺ 消息一定被记录"，不会出现"投递成功但消息丢了"
- ② 保证消息最终一定会发出去（这是 MQ 事务消息做不到的兜底）
- ③ 保证重复投递不会造成重复业务（至少一次投递 + 消费幂等 = 效果上恰好一次）
- ⑤ 兜底"消息发了但状态没更新"的中间态

**面试必答：本地消息表 vs RocketMQ 事务消息**

| | 本地消息表 | MQ 事务消息 |
|---|---|---|
| 可靠来源 | 业务库同事务，不依赖 MQ 特性 | 依赖 MQ 半消息 + 回查 |
| 耦合 | 与 MQ 解耦，换 MQ 不用改逻辑 | 强绑定 RocketMQ |
| 代价 | 多一张表 + 扫描任务；表会增长需归档 | 业务需实现回查接口 |
| 适用 | 通用、跨 MQ 中间件 | 已用 RocketMQ 的团队 |

#### 状态变更通知（复用本地消息表）

**状态迁移成功后，通知不能丢**——状态改了，求职者 / HR 必须收到通知。做法是**状态迁移与通知消息放同一个本地事务**（与投递创建同机制，只是 `biz_type` 不同）：

```
BEGIN;
  UPDATE delivery SET status='OFFER' WHERE id=123 AND status='INTERVIEW';   -- ① 乐观锁迁移
  INSERT local_message (biz_type='DELIVERY_EVENT', biz_id=123, status=0,
    payload={ event:'SEND_OFFER', from:'INTERVIEW', to:'OFFER',
              notifyTo:'SEEKER', seekerId:88, companyId:7 });
COMMIT;
```

之后定时发送 / 失败重试 / 对账，全部复用已有的 local_message 机制。

**通知映射（哪个事件通知谁）**：

| 事件 | 接收方 | 文案（示例） |
|---|---|---|
| CONTACT | 求职者 | HR 已与你发起沟通 |
| INVITE_INTERVIEW | 求职者 | 收到面试邀请 |
| SEND_OFFER | 求职者 | 恭喜，收到 Offer |
| REJECT | 求职者 | 投递未通过 |
| HIRE | 求职者 | 恭喜入职 |
| CANCEL | **HR** | 求职者取消了投递 |
| VIEW | — | 不通知 |

> 方向要点：HR 发起的事件通知求职者，求职者的 CANCEL 通知 HR——`payload.notifyTo` 决定接收方，不能假设总是通知求职者。

**定时清理积存消息**：

```
清理任务（每天凌晨，分布式锁防多实例）：
  ① 删除 status=2（已确认）且 update_time < now - 7天
  ② status=3（失败）→ 保留 + 告警，人工排查后再删
```

> 生产环境先归档到 `local_message_archive`（审计回溯），简历项目直接删即可。

### 6.3 统一搜索（职位 + 公司）★

求职者既能搜**岗位名**，也能搜**公司名**。

**索引结构：两个索引，不混排**（D-22）

| 索引 | 文档 | 主要字段 |
|---|---|---|
| `job_index` | 职位 | 标题、技能标签、描述、城市、薪资、经验、学历、分类 |
| `company_index` | 公司 | 名称、行业、规模、城市、在招职位数 |

**为什么不用单索引 + `type` 字段**：两类文档字段差异极大，**相关性评分量纲不同**——把"Java 工程师"和"某某科技公司"混在一个列表里排序，结果没有意义。

**按类型分组返回，前端分 Tab**（两个接口分别调，与 §6.1「前端分别调用」一致）：

```
GET /api/job/search?keyword=Java      → { jobs: [...] }
GET /api/company/search?keyword=Java  → { companies: [...] }
前端在同一搜索框下并行调用，分 Tab 展示
```

> 公司**无在招职位时仍可被搜到**，标注「暂无在招职位」——公司主页本身有价值，且与 D-20「企业随入驻产生」一致。

**MySQL → ES 数据同步**

**为什么不双写**：写完 MySQL 紧接着写 ES，一旦 ES 写失败或进程崩溃就永久不一致，且无法察觉。

**方案：MQ 异步同步 + 定时对账**

```
job 服务     职位增删改     → 本地事务 → 发 MQ（job.upsert / job.delete）
company 服务 企业信息变更   → 本地事务 → 发 MQ（company.upsert）
  → search 消费者写入 / 删除对应 ES 文档
  → 写 mq_consume_log 保证幂等

对账任务（每小时）
  → 比对 MySQL 与 ES 的 (id, update_time)
  → 缺失 / 过期的文档补齐
  → 输出差异数量，差异 > 阈值则告警
```

**搜索能力设计**：

- **分词**：IK 分词器（`ik_max_word` 建索引 / `ik_smart` 查询）
- **相关性**：`multi_match` + 字段权重（标题 > 技能标签 > 描述）
- **过滤**：城市、薪资区间、经验、学历用 `filter`（不参与打分，可走缓存）
- **分类**：`category_id` 做 filter + **聚合**，返回各分类职位数，驱动前端筛选器
- **高亮**：职位标题与技能关键词高亮
- **深分页**：超过 1000 页用 `search_after`，不用 `from + size`

**缓存设计（Redis）**：

| 问题 | 方案 |
|---|---|
| 缓存穿透（查不存在的职位） | 布隆过滤器 + 空值缓存（短 TTL） |
| 缓存击穿（热点职位过期） | 逻辑过期 + 互斥锁重建，或永不过期 + 异步刷新 |
| 缓存雪崩（大量同时过期） | TTL 加随机扰动 |

**面试必答：为什么不用 Canal？**
> Canal 监听 binlog 更实时、对业务无侵入，是生产环境更主流的选择。个人项目不用是因为它要额外部署 Canal Server、处理 DDL 变更和位点管理，成本偏高。我用 MQ + 对账，是为了在可控成本下把"一致性问题"和"补偿机制"讲清楚；如果上生产，我会选 Canal。

### 6.4 消息通知链路

```
业务事件 → MQ → notification 消费者
                    ↓
             写 notification / notification_receiver 表
                    ↓
             站内信可查 + （未来）WebSocket 实时推送
```

未来加 WebSocket 时的关键问题（**很好的面试题**）：

> **多实例部署下，用户 A 的长连接在实例 1，消息却由实例 2 消费到，怎么推给 A？**

方案：Redis Pub/Sub 广播（每个实例订阅同一个 channel，收到后检查本地是否有该用户连接）或 MQ 按实例维度路由。同时要考虑心跳保活、断线重连、单机连接数上限。

### 6.7 企业认证与招聘者准入 ★

**业务前提（D-14）**：平台**只允许企业招聘者**。个人不能以"我"的名义发职位，必须以"某公司的 HR"身份发布（BOSS 直聘模式）。因此 `job.company_id` 非空，发布链路必须做归属校验。

**招聘者准入 = 三重校验，缺一不可**（D-15 / D-16）：

```
实名通过 (auth)  AND  归属正常 (company_member)  AND  企业已认证 (company)
```

| 校验项 | 归属服务 | 数据来源 |
|---|---|---|
| 实名认证 | **auth** | `sys_user.real_name_status`（Mock：身份证校验位**真算法** + 模拟人证比对） |
| 归属认证 | company | `company_member.status = 正常` |
| 企业认证 | company | `company.verify_status = 通过` AND `business_status = 存续` |

**企业认证 = 三层核验**（D-24，借鉴 BOSS 直聘）：

```
① 用户创建企业 → 自动成为 OWNER，verify_status = 待审核
② 基础数据核验（三层之外，见下）
③ 通过风险评分决定走「法人授权」还是「人工审核」
```

| 层 | 确认什么 | 实现 |
|---|---|---|
| 一 个人实名 | "你是谁" | auth：姓名 + 身份证（校验位**真算法**）+ 人脸核身 Mock |
| 二 企业归属 | "你代表谁" | company：**风险评分** → 要求材料 |
| 三 法人强验证 | "公司同意你招人" | company：**法人授权令牌闭环** |

**基础数据核验**（D-18，无论走哪条通道都要做）：

```
统一社会信用代码校验码  → 真实算法（GB 32100-2015）
企业存在性 + 经营状态   → 阿里云市场 API
三要素一致性（名称 / 法人 / 信用代码）
结果写入 company_verify_record 留档（含第三方返回原文）
```

**第二层：风险评分（简单加权，不引规则引擎框架）**

| 维度 | 加分 | 减分 |
|---|---|---|
| 工商经营状态 | 存续 | 注销 / 吊销 → **直接拒** |
| 申请人实名 | 已认证 | 未认证 |
| 邮箱域名 | 企业域名 | 免费邮箱（qq/163） |
| 材料完整度 | 有授权书 / 在职证明 | 缺 |
| 企业成立年限 | ≥ 3 年 | < 1 年 |
| 历史记录 | 首次申请 | 同企业曾被驳回 |

```
低风险      → 材料齐全 + 企业邮箱验证 → 自动通过
中 / 高风险  → 法人授权 或 人工审核
```

**第三层：法人授权令牌闭环**（⚠️ 法人**无需注册账号**）

```
① 提交认证 → 调 CompanyVerifier 得到法人姓名
② 生成授权令牌（随机、一次性、有有效期）→ 写 company_authorization
③ 授权链接发给法人（邮件 / 短信）
④ 法人打开链接 → 填写姓名 + 身份证（人脸 Mock）完成实名
⑤ 法人确认授权 → status = 已授权
⑥ 申请人获得企业招聘权限
```

> **为什么是"法人主动授权"而不是"姓名比对"**：姓名是弱证据（重名率极高），法人本人完成实名并点击同意才是强证据——授权来自法人行为，不是系统推断。查到法人姓名的唯一作用，是**知道该找谁授权**。

**认证状态与职位状态联动** ⚠️（易漏项）：

```
企业 待认证      → 可建职位【草稿】，不可上线
企业 已认证      → 职位可【上线】招聘中
企业认证被撤销   → 该企业已上线职位【批量下线】+ 通知 HR
```

漏掉最后一条，就会出现**"企业已注销、职位仍挂线"**的数据不一致。

> **企业认证恢复后，被强制下线的职位不自动重新上线**——HR 可能早已不想招了，应由 HR 手动重新上线。
> 三种下线来源通过 `job.offline_reason` 区分：手动 / 企业认证失效 / 管理员下架（另有已招满、已过期）。

**OWNER 缺失**（D-17）：创建者离职后企业账号由谁管理？**不建专门机制**——OWNER 的唯一数据源是 `company_member.role = 'OWNER'`，更换 OWNER 走**已有的管理端接口**（管理员改角色）；法人（`is_legal_rep`）可凭实名信息向平台申请接管。

**接口抽象**（D-18）：

```java
public interface CompanyVerifier  { CompanyVerifyResult verify(CompanyVerifyRequest req); }
public interface RealNameVerifier { RealNameResult verify(String name, String idCard); }
// Mock 实现：开发默认 + 降级兜底（真校验位算法 + 模拟数据源）
// 阿里云实现：正式环境，配置开关 hirehub.verify.channel 切换
```

> ⚠️ 阿里云市场的 `AppCode` 走**环境变量**注入，本地配置加入 `.gitignore`；免费额度耗尽时**自动降级到 Mock**（见 D-18）。

> ⚠️ **禁止爬取天眼查 / 企查查等第三方网站**：违反用户协议、可能构成不正当竞争，绕过反爬可能触及《刑法》第 285 条，且面试是明显负分项。走**授权付费 API**（见 D-18）。

### 6.8 岗位偏好与人才匹配 ★

**两个方向**：偏好既驱动**正向推送**（系统推职位给求职者），也驱动**反向曝光**（简历被 HR 搜到）。

#### 正向：定期推送匹配职位

```
resume 服务定时任务（分布式锁 / 按 userId 分片，防多实例重复推）
  → 扫 job_preference（job_status ∈ {随时到岗, 考虑机会}）
  → 按偏好查 ES：期望分类 + 城市 + 薪资区间交集
  → 过滤：push_record 已推过的职位、blocked_company_ids 里的公司
  → 频率控制：每周 ≤ N 条
  → 写 push_record → 发 MQ → notification 推送
```

**匹配用规则，不做推荐算法**：分类 + 城市 + 薪资区间交集即可。简历项目做推荐是伪需求，规则匹配够用且**匹配逻辑讲得清**。

**三个必须处理的点**：

| 问题 | 方案 |
|---|---|
| 多实例重复推 | 分布式锁（或按 userId 分片） |
| 同一职位推两次 | `push_record` 的 `uk (user_id, job_id)` |
| 推送太频骚扰用户 | 频率上限（每周 ≤ N 条），靠 `idx (user_id, push_date)` 统计 |

#### 反向：简历被 HR 搜到（隐私分级，见 D-23）

**核心原则：默认最小可见，由用户主动放开。**

```
可被搜到  ⟺  job_status ∈ {随时到岗, 考虑机会}  AND  简历 status = 公开
```

四层控制：

| 层 | 作用 |
|---|---|
| **求职状态** | 「在职-暂不考虑」→ 完全不出现 |
| **匿名化** | HR 默认只看到"张先生 / 5 年经验 / 某互联网公司"，**看不到姓名与联系方式** |
| **联系方式需同意** | HR 发起沟通、用户同意后才展示真实信息 |
| **屏蔽公司** ⭐ | 不让自己现在的公司搜到（在职找工作必备） |

**可见范围也要收**：只有**已认证企业的 HR** 能搜人才库，且每次查看**留痕**。否则等于开放了一个批量爬取简历的接口。

**简历索引**：`resume_index` **只索引允许被搜到的简历**。用户关闭曝光时需**立即**从索引删除——这一点和职位索引不同：**隐私状态变化必须实时生效，不能等对账任务**。

### 6.9 面试状态机（与投递解耦）★

**投递 : 面试 = 1 : N**（一个投递可有多轮面试）。两者是**两套独立状态机**：

```
投递状态 = 整体流程走到哪一步（PENDING → … → INTERVIEW → OFFER）
面试状态 = 「INTERVIEW 这一步」内部，具体安排了什么
```

**面试状态（5 个，终态 3 个）**：

| 状态 | 语义 |
|---|---|
| SCHEDULED | 已安排，待求职者确认 |
| CONFIRMED | 已确认 |
| COMPLETED | 已完成（有反馈）· 终态 |
| REJECTED | 求职者拒绝 · 终态 |
| CANCELLED | 已取消（任一方）· 终态，记 `cancelled_by` + `cancel_reason` |

**迁移矩阵**：

| 从 | 到 | 事件 | 发起方 |
|---|---|---|---|
| SCHEDULED | CONFIRMED | InterviewConfirmed | 求职者 |
| SCHEDULED | REJECTED | InterviewRejected | 求职者 |
| SCHEDULED | CANCELLED | InterviewCancelled | 任一方 |
| CONFIRMED | COMPLETED | InterviewCompleted | HR |
| CONFIRMED | CANCELLED | InterviewCancelled | 任一方 |
| CONFIRMED | SCHEDULED | InterviewRescheduled | HR（改期需重新确认） |

**与投递的解耦（关键）**：

1. **面试取消 / 拒绝不回退投递状态**——投递仍停在 `INTERVIEW`，求职者拒绝一轮后 HR 可重新发起新一轮（`round` 递增）
2. **面试反馈不自动流转投递状态**——反馈只是 `interview_feedback` 记录，是 HR 的"决策依据"而非"决策本身"；HR 看后手动发起投递事件 `SEND_OFFER` / `REJECT`
3. **`round` 是面试维度，不进投递状态机**——投递只知道自己"在面试中"，不知道第几轮

**事件与通知**：面试事件同样在同事务写 `local_message` 通知对方（`InterviewRescheduled` 通知求职者、`InterviewCancelled` 通知另一方），复用 D-01 机制。

## 8. 横切设计

### 8.1 统一响应与异常

- `Result<T>` 统一响应体，含 `traceId` 便于排查
- `@RestControllerAdvice` 全局异常处理
- 错误码分段：`10xxx` 通用、`20xxx` 认证、`30xxx` 业务

### 8.2 幂等设计

| 场景 | 方案 |
|---|---|
| 重复投递 | Redis SETNX（`delivery:{jobId}:{resumeId}`）+ DB 唯一索引兜底 |
| MQ 重复消费 | `mq_consume_log` 唯一索引 / Redis 去重 |
| 重复提交表单 | 前端传 `requestId`，服务端 Redis 去重 |
| 并发更新计数 | Redis INCR 或 DB 乐观锁 |

### 8.3 限流与降级

- **职责划分**：网关做**入口限流**（IP / 接口维度），Sentinel 做**服务级熔断降级**，避免重复配置
- **规则持久化**：Sentinel 规则默认存内存，**重启丢失** → 持久化到 Nacos（`sentinel-datasource-nacos`）
- **Feign 降级**：用 `fallbackFactory`（比 `fallback` 好，能拿到异常原因）

### 8.4 链路追踪

- **Micrometer Tracing** + traceId 贯穿
- 透传链路：网关 → HTTP Header → Feign（`RequestInterceptor`）→ MQ（消息头）→ 消费者

⚠️ **两个坑**：
1. **Feign 不会自动传递 header**，必须写 `RequestInterceptor`，否则下游拿不到 `X-User-Id`
2. **异步线程 / 线程池会丢失 ThreadLocal**，需要 `TransmittableThreadLocal`（TTL）或手动传递

### 8.5 数据权限

- 统一从请求头取 `X-Company-Id` / `X-User-Id`，**绝不信任前端传入的归属 ID**
- 企业隔离可用 MyBatis-Plus 多租户插件自动拼接 `company_id`

## 9. 环境与部署

### 9.1 docker-compose 组件

| 容器 | 镜像 | 端口 | 内存建议 |
|---|---|---|---|
| mysql | `mysql:8.0` | 3306 | 512M |
| redis | `redis:7-alpine` | 6379 | 256M |
| nacos | `nacos/nacos-server:v3.0.3` | 8848/8080/9848/9849 | 1G |
| rabbitmq | `rabbitmq:4-management` | 5672/15672 | 256M |
| elasticsearch | `docker.elastic.co/elasticsearch/elasticsearch:8.x` | 9200 | **2G** |
| minio | `minio/minio` | 9010/9011 | 256M |

### 9.2 内存预算 ⚠️

| 项 | 估算 |
|---|---|
| 中间件合计 | ≈ 4.5 GB |
| 8 个服务（IDE 运行，每个 ≈ 400MB） | ≈ 3.2 GB |
| IDE + 浏览器 + 系统 | ≈ 4 GB |
| **合计** | **≈ 12 GB** |

> **建议 16GB 起步，24GB 舒适。** ES 是最大开销，本地可把堆调小（`-Xms512m -Xmx512m`）并关闭不必要的副本分片（`index.number_of_replicas: 0`）。

### 9.3 Docker 化关键坑 ⚠️

1. **Nacos 注册的 IP 必须可达**：容器内默认注册 `172.x.x.x`，宿主机/网关连不上。
   显式指定：`spring.cloud.nacos.discovery.ip=<宿主机可达IP>`
   这是微服务 Docker 化的头号坑。
2. **启动顺序**：用 `healthcheck` + `depends_on: condition: service_healthy`，否则服务比 Nacos 先起来会崩。
3. **容器资源限制**：给每个容器加 `mem_limit` / `deploy.resources.limits`。
4. **ES 安全配置**：ES 8.x 默认开启 TLS + 账号密码，本地要么配好证书，要么显式关闭（仅限本地）。

## 11. 简历亮点与面试准备

### 11.1 建议深挖的 6 个亮点

| # | 亮点 | 能体现的能力 |
|---|---|---|
| 1 | **投递最终一致性**（本地消息表 + 对账补偿） | 分布式事务取舍、可靠性设计 |
| 2 | **统一搜索**（职位 + 公司双索引 + 多级缓存 + 布隆过滤器 + 缓存三防） | 搜索建模、高并发读优化 |
| 3 | **多维度身份与权限模型**（全局角色 + 企业维度角色；RBAC + 水平越权 + 注册提权） | 安全意识、权限建模（比"我用了 JWT"值钱） |
| 4 | **简历解析 + ES 全文检索** | 辨识度高，招聘平台专属功能 |
| 5 | **企业认证与招聘者准入**（三层核验 + 法人授权 + 状态联动 + 三方接口抽象） | 领域建模、合规意识、三方集成设计 |
| 6 | **求职者隐私分级**（求职状态 + 匿名化 + 联系方式同意 + 屏蔽公司） | 隐私合规、产品思维（面试很吃这套） |

### 11.2 高频追问清单（提前准备答案）

1. 本地消息表和 MQ 事务消息的区别？为什么选前者？
2. 消息重复消费怎么办？消息丢失怎么发现？
3. 为什么不用 Canal 同步 ES？双写为什么不行？
4. JWT 怎么实现登出？无状态怎么撤销？
5. 缓存穿透/击穿/雪崩分别怎么解决？布隆过滤器误判怎么办？
6. 你怎么防止一个 HR 看到别家公司的简历？
7. Feign 调用怎么传递用户身份？异步线程里会丢吗？
8. Sentinel 规则重启丢失吗？怎么持久化？
9. 为什么最后没用 Seata？（**这题答好了是加分项**）
10. 网关是怎么做鉴权的？下游服务还校验吗？为什么？
11. 深分页怎么做的？`from + size` 有什么问题？
12. 你的服务边界是怎么划分的？为什么 `job` 和 `search` 没拆开？
13. 注册接口怎么防止用户把自己注册成管理员？（**经典提权漏洞，答不出很致命**）
14. 为什么把"雇佣者"放在 `company_member` 而不是账号表？一个账号能同时是求职者和 HR 吗？
15. 企业角色为什么不写进 JWT？HR 被移除后权限怎么立即失效？
16. 管理员为什么要加？没有管理员你的企业认证流程能走通吗？
17. 为什么不做服务端"身份切换"接口？（要点：**多端状态互踩 + 切换接口本身是提权面 + 接口语义已表达身份**）
18. 为什么平台不允许个人发职位？责任主体怎么追溯？
19. 企业认证通过前能不能发职位？（要点：**分层——草稿可建、上线需认证**，并说明为什么宽松策略会让认证失去价值）
20. 实名认证放 auth 还是 company？为什么？（要点：**实名是"人"的终身属性，归属是"关系"且会变**）
21. 法定代表人为什么不给额外权限？OWNER 离职了企业账号怎么办？（要点：**法律身份 ≠ 产品权限**；法人做兜底 + 转移机制）
22. 企业工商数据从哪来？（⚠️ **必须答"授权付费 API"，绝不能答爬第三方网站**）
23. 面试官为什么不做成固定角色？（要点：**面试官是按面试实例授权的；固定角色会导致跨岗位时看到全部候选人**。本期简化为 HR 代录 + `interviewer_name` 文本记录）
24. 平台的企业数据从哪来？为什么不预置企业库？（要点：**工商数据不含求职者关心的信息 + 未经确认的展示有合规与责任风险 + 会稀释"企业信息全量可信"的优势**，见 D-20）
25. HR 和 OWNER 为什么要区分？（要点：**删除仅 OWNER**，加上生成邀请码 / 调整成员角色；**每个角色都要有独占的操作，否则就是多余的抽象**，见 D-21）
26. 搜公司和搜职位为什么用两个索引、不做混排？（要点：**两类文档字段差异大、相关性评分量纲不同，混在一个列表里排序没有意义**，见 D-22）
27. 定时推送怎么保证多实例不重复推、同一职位不推两次？（要点：**分布式锁防多实例 + `push_record` 唯一索引去重 + 频率上限防骚扰**，见 §6.8）
28. 简历被 HR 搜到，你怎么保护求职者隐私？（要点：**默认最小可见**——求职状态前置 + 匿名化 + 联系方式需用户同意 + **屏蔽公司** + 仅认证企业 HR 可搜且留痕，见 D-23）
29. 你凭什么相信申请人是这家公司的？（要点：**三层核验**——实名确认"你是谁"、归属确认"你代表谁"、法人授权确认"公司同意你招人"，见 D-24）
30. 为什么法人授权用"本人点击同意"而不是"系统比对姓名"？（要点：**姓名是弱证据、重名率极高；法人主动行为才是强证据**）
31. 投递后用户改了简历，HR 看历史投递看到哪个版本？（要点：**快照（投递那一刻）**——投递是时间点事件，事后修改不追溯；简历删了投递也不断链，见 D-26）
32. 投递状态机为什么用"事件 + 迁移表"，而不是一堆 if/else？（要点：**事件驱动 + 查表迁移 + 权限绑在事件上**；新增迁移只加一行表项；并发用乐观锁，见 D-27 / §6.2）
33. 状态改了但通知没发出去怎么办？（要点：**状态迁移与通知消息放同一个本地事务**，`local_message` 兜底 + 定时发送 + 对账 + 定时清理，见 §6.2 / D-01）
34. 面试取消为什么不回退投递状态？面试反馈为什么不自动改投递状态？（要点：**两套独立状态机**——投递是整体流程、面试是 INTERVIEW 一步内部；反馈是 HR 的决策依据不是决策本身，见 D-28 / §6.9）

### 11.3 关于实时通话（建议暂缓）

| 方案 | 评价 |
|---|---|
| **WebSocket 站内消息**（在线状态/已读回执） | ✅ **推荐**。可讲"多实例长连接消息路由"，性价比高 |
| **WebRTC 实时通话** | ⚠️ **暂缓**。需要信令 + STUN/TURN（coturn）+ HTTPS，面试追问 NAT 穿透、SDP 协商、丢包对抗很难接住 |

**建议**：先把"WebSocket 实时消息"做出来，通话功能等主项目跑通、简历投出去有反馈后再评估。

## 12. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 版本太新，教程对不上 | 环境卡壳、进度停摆 | 已列 §2.2 踩坑清单；**先跑通 Nacos + Gateway 最小链路**再铺业务 |
| 组件太多，范围失控 | **烂尾**（最大风险） | 严格执行分期，每期必须有可演示产出 |
| 内存不足 | ES/Nacos 起不来 | 见 §9.2；必要时 ES 堆调 512M、副本数设 0 |
| Knife4j 与 Boot 3.5 不兼容 | 文档页打不开 | 一期用原生 springdoc 2.9.1 |
| 简历写了讲不出的组件 | 面试反被扣分 | 只写做透的 3–4 个亮点，宁可少写 |
| 注册接口接受客户端角色字段 | **提权漏洞**，被问穿很致命 | 注册硬编码只建 `SEEKER`；`PLATFORM_ADMIN` 只由初始化脚本产生（§6.1） |
| 企业认证爬取第三方数据 | **法律风险 + 面试负分** | 走**授权付费 API** + Mock 实现，禁止爬取（D-18 / §6.7） |

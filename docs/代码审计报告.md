## 1. 功能缺陷

### F-01【高】已下线职位永远无法重新上线，与 Q-08 设计矛盾
- 文件：`hirehub-job/src/main/java/com/ll/hirehub/job/service/JobService.java:86-88`
- 架构文档 §6.10 明确"企业认证恢复后，被强制下线的职位由 HR 手动重新上线"。但 `publish` 只放行 `status=0`，`offline` 只能 1→2，**不存在 2→1 的任何路径**，被下线职位全部成为死数据。
```java
if (job.getStatus() == null || job.getStatus() != 0) {
    throw new BusinessException("仅草稿状态可上线");
}
```
- 修复：`publish` 放行 `status ∈ {0, 2}`，重新上线时清空 `offlineReason`、重置 `publishTime`。
- 回归测试：`JobServiceTest#publishAllowsRepublishOfflineJob`（@Disabled，修复后启用）。

### F-02【高】HR 查看详情的自动 VIEW 迁移无乐观锁，可"复活"已取消投递
- 文件：`hirehub-delivery/src/main/java/com/ll/hirehub/delivery/service/DeliveryService.java:128-137`
- `selectById` → `updateById` 之间无保护。时序：HR 打开详情（读出 PENDING）→ 求职者并发 CANCEL（已提交 CANCELLED）→ HR 的全字段 `updateById` 把状态写回 VIEWED，**终态被逆迁**，违反 D-27。且与同文件 `applyEvent`（:159-162，`.eq(status, current)` 条件更新）形成两套不一致写法，违反 §6.2"UPDATE ... WHERE status=前态"约定。
- 修复：改为 `update(null, new LambdaUpdateWrapper<Delivery>().eq(id).eq(status, PENDING).set(status, VIEWED))`；affected=0 无需报错（VIEW 幂等）。

### F-03【高】面试状态机迁移无乐观锁，并发下终态互踩
- 文件：`hirehub-interview/src/main/java/com/ll/hirehub/interview/service/InterviewService.java:145-150`
```java
private void transition(Interview iv, InterviewEvent event, String actor) {
    InterviewStatus target = stateMachine.apply(current, event, actor);
    iv.setStatus(target.name());
    interviewMapper.updateById(iv);   // 无 status=前态 条件
}
```
- 两个并发请求（HR COMPLETE 与求职者 CANCEL）各自通过校验后互相覆盖，后写胜出。`cancel()`（:115-117）、`reschedule()`（:126-127）在 transition 后再追加一次 `updateById`，进一步放大窗口。
- 修复：transition 改为 `UPDATE interview SET status=#{target} WHERE id=#{id} AND status=#{current}`，affected=0 抛"状态已被他人修改"；cancel/reschedule 的附加字段合并进同一次条件更新。

### F-04【中】面试创建不校验投递状态，两套状态机可失序
- 文件：`hirehub-interview/.../service/InterviewService.java:41-46`
- 可对 `REJECTED/CANCELLED` 终态投递发起面试邀约；且创建面试不触发投递的 `INVITE_INTERVIEW` 事件，若前端漏调 delivery events 接口，投递停在 PENDING 而面试已存在，D-28 双状态机失序且后端无兜底。
- 修复：create 校验 `delivery.getStatus() ∈ {PENDING, VIEWED, COMMUNICATING, INTERVIEW}`，终态拒绝。
- 回归测试：`InterviewServiceTest#createRejectsTerminalDelivery`（@Disabled）。

### F-05【中】复核撤销的自调用导致 @Transactional 失效
- 文件：`hirehub-company/.../service/CompanyRecheckService.java:107-151`
- `recheckOnce → recheckOne → this.revoke(...)` 同类自调用，`revoke` 的 `@Transactional` 被绕过：① 撤销 update 与 verify_record insert 不再原子；② `afterCommit()` 退化为立即执行发 MQ，踩坑 #14 的"先发事件后回滚"保护实际不存在。
- 修复：`revoke` 拆独立 Bean / 注入自身代理（@Lazy）/ TransactionTemplate 包裹。

### F-06【中】schedule() 的"立即提醒"路径在事务内直发 MQ
- 文件：`hirehub-interview/.../mq/InterviewReminderService.java:101-108`
- `delayMs <= 0` 时 `fire()` 在 `@Transactional` 内直接 `convertAndSend`，违反"外部副作用注册在 afterCommit"约定（§6.4 / 踩坑 #14）。事务回滚 → 幽灵提醒；且 `fire()` 每次生成新 UUID messageId，兜底扫描补发时幂等键不同 → 重复提醒。
- 修复：`delayMs <= 0` 分支改为以 score=now 放入 ZSet 由 Poller 触发，或将 fire 注册到 afterCommit。

### F-07【中】job/company 的 ES 对账只补不清，陈旧文档永久可搜
- 文件：`hirehub-job/.../search/JobSearchService.java:168-176`、`hirehub-company/.../search/CompanySearchService.java:110-116`
- 两个对账任务只把 DB 中有效记录重灌索引，从不删除 ES 多余文档。"下线/撤销"的 upsert 消息一旦丢失（正是对账存在的意义），陈旧文档带 `status=1` 永久可搜。对照组 `ResumeIndexService.reconcile:200-217` 做了双向比对，才是 §6.3 承诺的语义。
- 修复：参照 `ResumeIndexService` 增加反向扫描（search_after 取 ES 全量 id），清理 DB 中不存在或状态不符的文档。

### F-08【中】企业搜索 industry 过滤基本失效
- 文件：`hirehub-company/.../search/CompanySearchService.java:44, 77`
- `company_index.industry` 映射为 `text + ik_max_word`（无 keyword 子字段），查询却用 `term` 精确过滤，IK 切词后全串永远匹配不上。
- 修复：mapping 改 `text + fields.keyword`，term 打到 `industry.keyword`（需重建索引）。

### F-09【中】对账把消息打回 PENDING 无状态条件，与消费回执竞争
- 文件：`hirehub-delivery/.../mq/LocalMessageRelay.java:91-96`（另 :37-41、:59-70 同病）
- reconcile 查询（SENT）与更新之间，消费回执可能刚把消息置 CONFIRMED，无条件 update 把它翻回 PENDING → 已确认消息被重投。迟到的 confirm ack 也会把 FAILED/CONFIRMED 翻回 SENT。
- 修复：三处更新都加 `.eq(status, 期望前态)` 前置条件。

### F-10【低】draft/offline/delete 缺实名认证校验，与接口契约不符
- 文件：`hirehub-job/.../service/JobService.java:37, 98, 113`
- §7 接口清单对 `POST /draft`、`POST /{id}/offline`、`DELETE /{id}` 均标注"[OWNER/HR] 实名"，实际仅 `publish` 校验了 `authClient.getRealNameStatus`。
- 修复：抽 `requireRealName(userId)` 三处复用。

### F-11【低】实名认证可重复提交且不做身份证查重
- 文件：`hirehub-auth/.../service/AuthService.java:261`
- ① 同一身份证可绑多账号（无 `id_card_no` 查重）；② 已认证用户可重复提交直接覆盖姓名与身份证。
- 修复：认证前查重；`realNameStatus==1` 拒绝或走独立"变更实名"流程。

### F-12【低】登录锁定可被滥用为对受害者的 DoS
- 文件：`hirehub-auth/.../service/LoginAttemptGuard.java:35`
- 锁定维度只有用户名。攻击者掌握用户名即可每 15 分钟制造 5 次失败让受害者永久无法登录（锁定期内正确密码也拒，D-39）。
- 修复：叠加 IP/设备维度或提供管理员解锁通道；至少在 ADR 记录该残余风险。

### F-13【低】注册并发冲突被兜底成 500
- 文件：`hirehub-auth/.../service/AuthService.java:50-63`

## 3. 消息可靠性 / 架构不符合项

### R-01【高】重复消费不补发消费回执 → 对账误杀为 FAILED

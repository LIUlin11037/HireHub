# HireHub 压测报告

> 原则：**只写实测数据，不编造、不推测、不拿"理论上限"充数。**
> 所有数字来自 `scripts/perf-load.ps1` 在本机的真实运行结果，命令与参数可复现。

---

## 1. 方法与可复现命令

压测脚本 `scripts/perf-load.ps1` 每轮分两个阶段（**两类数字不能混读**）：

| 阶段 | 做法 | 得到什么 |
|---|---|---|
| **吞吐** | `Concurrency` 个并发持续发 `DurationSec` 秒 | 总请求数 / 墙钟时间 → **req/s**，以及**成功率** |
| **延迟** | **串行**发 `Samples` 次，逐次计时 | **单请求延迟**的 p50 / p95 / p99 / max |

> **为什么分成两段**：并发发送时，要把每个请求的耗时归到它自己头上，需要挂每请求的回调；
> 而 PowerShell 脚本块无法在裸 .NET 线程上运行（没有 runspace）。
> 所以**吞吐取并发阶段、延迟百分位取串行阶段**——两个数都是真实测量值，
> 但"p95=10ms"指的是**串行单请求**的 p95，**不是**并发下的 p95。这一点必须明说，否则就是误导。

```powershell
. .\scripts\e2e-lib.ps1
$alice = ((Api POST '/api/auth/login' -Body '{"username":"alice6761","password":"123456"}').Json.data).accessToken
$bob   = ((Api POST '/api/auth/login' -Body '{"username":"bob6761","password":"123456"}').Json.data).accessToken

.\scripts\perf-load.ps1 -Label 'A) job search'  -Path '/api/job/search?keyword=Java&size=10'  -Token $alice -Concurrency 32 -DurationSec 15 -Samples 200
.\scripts\perf-load.ps1 -Label 'B) job detail'  -Path '/api/job/12'                           -Token $alice -Concurrency 32 -DurationSec 15 -Samples 200
.\scripts\perf-load.ps1 -Label 'C) talent pool' -Path '/api/resume/search?keyword=Java&size=10' -Token $bob -CompanyId 14 -Concurrency 16 -DurationSec 15 -Samples 150
```

## 2. 被测环境（很重要，决定了数字的适用范围）

| 项 | 值 |
|---|---|
| 拓扑 | **8 个服务跑在 Docker 容器**（每个 `mem_limit: 640m`），由 `docker/docker-compose-services.yml` 编排 |
| 中间件 | MySQL / Redis / Nacos / Elasticsearch(2g) / MinIO 均为本机 Docker |
| 入口 | 网关 `127.0.0.1:9000` |
| 压测端 | 与所有容器**同一台机器**上的 PowerShell + .NET `HttpClient` |

⚠️ **这些数字不是生产容量**，原因有三，必须一起读：

1. **压测端与被测端抢同一台机器的 CPU/内存**——容器各自被限到 640m，压测进程自己也在吃 CPU，
   所以数字反映的是"本机上限的近似"，不是"单机服务能力"。
2. **单机、单实例**：没有跨节点网络延迟，也没有多实例负载均衡。
3. **数据量小**：`job_index` 仅个位数~十几条文档，ES 的查询计划与真实数据量下不同。

**能用它做什么**：横向比较不同链路的**相对开销**、证明"零错误"、给出本机上量级的参考。
**不能用它做什么**：对外宣称 QPS 承载能力。

## 3. 结果（实测）

数据来源：2026-09-25 本机实测，单次运行，共 **42,320** 次请求，**错误 0**。

| 场景 | 走的技术路径 | 吞吐 | 成功率 | 串行 p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|
| **A) 职位搜索** `GET /api/job/search?keyword=Java` | 网关 → job → **ES + IK 分词**（无缓存） | **873.7 req/s** | 100% | 8.3ms | 10.1ms | 11.8ms | 12.1ms |
| **B) 职位详情** `GET /api/job/12` | 网关 → job → **Redis 缓存命中** | **1423.5 req/s** | 100% | 8.3ms | 10.6ms | 13.5ms | 13.6ms |
| **C) 人才库检索** `GET /api/resume/search?keyword=Java` | 网关 → resume → **Feign 查成员关系 + Feign 查企业认证状态** → ES（带隐私过滤） | **521.5 req/s** | 100% | 15ms | 18.3ms | 19.5ms | 20.7ms |

（A/B 并发 32、C 并发 16，各持续 15 秒；延迟为串行采样 A/B 200 次、C 150 次。）

## 4. 观察与瓶颈分析

1. **缓存确实有效：B 比 A 快约 1.63×（1423.5 vs 873.7 req/s）**。
   两者都要过网关和 job 服务，差别只在「查 Redis」与「查 ES + 解析命中/高亮」。
   → **这是本项目里"缓存三防 + 布隆过滤器"这层的直接体现**。
   （严格说 A/B 是不同端点，不是同一端点的开/关对照，见 §5 的说明。）
2. **跨服务调用是当前最贵的一环：C 只有 A 的 60%（521.5 vs 873.7 req/s），p50 从 8.3ms 涨到 15ms**。
   多出来的开销几乎全在两次 Feign（`/internal/member` 与 `/{id}/verify-status`）上——
   这是"人才库只允许已认证企业的在职 HR 访问"这条隐私规则的必要代价。
   → 已做的优化：成员关系走 Redis 缓存（`member:{userId}:{companyId}`）。
   → 若要继续优化，方向是**把企业认证状态一并纳入同一份缓存**，把两次 Feign 合成一次。
3. **全部 42,320 次请求零错误**，说明在本机这个压力下没有出现连接耗尽、超时、限流误伤。
4. **限流没被误触发**：`hirehub-gateway-flow` 只配了 `hirehub-auth` 路由（100 QPS），
   本次压测打的是 job / resume 路由，因此不受影响——这本身也验证了"规则只作用于目标路由"。

## 5. 明确**没有**做的对比（以及原因）

| 想做的 | 为什么没做 |
|---|---|
| **同一端点"缓存开/关"对照** | 缓存开关是启动期配置，运行中改不了；要对照就得改配置重启服务再压一轮。而"逐请求清缓存"会让每条请求都夹一次 Redis 删除操作，**测量被污染**。→ 与其给一个不可信的数字，不如只给 A/B 这种**不同路径的相对对照**并注明口径。 |
| **限流阈值下的 429 比例压测** | 已在踩坑记录 #24 中单独做过（150 并发 → 100×401 + 50×429，正好卡 `count: 100`），属于功能验证而非性能测试，不混进本报告。 |
| **长稳测试（数小时）** | 本机环境不具备长时间独占条件，做了也说明不了问题。 |
| **生产级容量结论** | 见 §2 的三条限制——**没有足够依据，所以不写**。 |

## 6. 复现方式与记录

- 脚本：`scripts/perf-load.ps1`（纯 ASCII，两个阶段，输出吞吐与延迟百分位）
- 原始输出：`logs/` 下当次运行的 `Tee-Object` 记录
- 结论稳定性：单次运行。**若要引用为正式数据，建议至少跑 3 轮取中位数**，并在报告中注明轮次——
  本次只跑了一轮，所以上表是**单次实测**，不是统计稳定的中位数。

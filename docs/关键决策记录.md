# HireHub 关键决策记录（ADR）

> 本文档记录 HireHub 项目在设计与选型过程中做出的**关键决策**，采用 ADR（Architecture Decision Record）格式。
>
> 目的有两个：
> 1. **防止后期返工**——每个决策都写清"为什么这么选"和"为什么不选另一个"
> 2. **面试话术弹药库**——面试官追问设计取舍时，答案在这里
>
> 架构与实现细节见 `docs/架构与实施文档.md`，本文档只记录**决策本身**。

> **文档纪律（强制）**：
> 1. 凡产生**重大决策**，必须按下面 ADR 格式新增到本文档，并更新顶部决策索引与状态图例。
> 2. 决策落地后若架构 / 实现有变化，必须**实时同步** `docs/架构与实施文档.md`。
> 3. 踩过的坑记入 `docs/踩坑记录.md`，不重复踩。

## D-01 分布式事务方案

### 背景

招聘平台的核心跨服务写链路是「投递」：

```
delivery 写投递记录  →  job 投递数 +1  →  notification 通知 HR
```

一次业务操作跨三个服务，需要决定如何保证跨服务数据一致性。

### 可选方案

1. **Seata AT 模式** —— 全局事务，两阶段提交 + `undo_log` 自动回滚
2. **本地消息表 + MQ 最终一致性** —— 业务数据与消息同库同事务写入，异步投递 + 对账补偿
3. **RocketMQ 事务消息** —— 半消息 + 事务状态回查

### 决策

**选方案 2。**

> 原选型中包含 Seata，本决策将其**移除**。

### 理由

- 投递是**高频写**场景，Seata AT 的全局锁 + `undo_log` 开销不划算
- **「通知失败」本来就不该回滚整笔投递**——用户投递已经成功了，通知没发出去应当重试，而不是撤销
- 投递计数**短暂不准不影响正确性**，属于可接受的最终一致
- 与具体 MQ 中间件解耦，将来换 MQ 不需要改业务逻辑

### 代价与风险

- 需要额外一张 `local_message` 表和扫描任务
- 该表随业务增长，需要归档/清理策略
- 引入「至少一次投递」语义 → **消费端必须做幂等**，否则会重复业务

### 面试价值

「为什么不用 Seata」是**加分题**。答"评估过 AT 模式，但该场景是高频写、通知失败不该回滚、计数短暂不准可接受，所以选最终一致 + 对账补偿"体现架构判断力；只会说"我用了 Seata"反而容易被追问穿。

## D-02 认证鉴权框架

### 背景

需要认证与鉴权能力。原选型中只列了 `JWT`，没有认证框架。

### 可选方案

1. **裸 JWT + 自定义拦截器** —— 手写 token 解析与校验
2. **Spring Security 6 + JWT** —— 官方安全框架 + JWT 无状态凭证
3. **Session + Redis** —— 服务端会话

### 决策

**选方案 2。**

### 理由

- 方案 1 无法自然覆盖**方法级鉴权（RBAC）**、密码编码、安全响应头等，容易被判定为"只会写 demo"
- Spring Security 是行业标准，能顺理成章地引入 `@PreAuthorize` 与角色模型
- 保留 JWT 的无状态优势，同时用 Redis 解决"无状态无法撤销"的问题

### 配套设计

| 项 | 方案 |
|---|---|
| 双 token | accessToken 30min + refreshToken 7d（存 Redis，可撤销） |
| 登出 | accessToken 的 `jti` 写入 Redis 黑名单，TTL = 剩余有效期 |
| 全局角色 | 写入 token |
| 企业角色 | **不写 token**（成员关系会变，避免撤权延迟） |

### 代价与风险

- Boot 3 的 Security 配置方式与 Boot 2 **完全不同**（`SecurityFilterChain` Bean，不是 `WebSecurityConfigurerAdapter`），网上大量教程已过时
- 网关鉴权模式下，**下游服务需手工构建 `SecurityContext`**，否则 `@PreAuthorize` 全部拒绝或全部放行

### 面试价值

登出/撤销、双 token 设计、越权防护（水平 / 垂直 / 注册提权）——比"我用了 JWT"值钱得多。

## D-03 版本路线

### 背景

选型确定后需要锁定各组件版本。Spring Cloud Alibaba 的版本与 Spring Boot / Spring Cloud 强绑定，必须先选路线。

### 可选方案

1. **稳妥路线** —— Spring Boot 3.2.4 + SCA 2023.0.1.0 + Nacos 2.3.2
2. **求新路线** —— Spring Boot 3.5.0 + SCA 2025.0.0.0 + Nacos 3.0.3

### 决策

**选方案 2（求新路线）。**

### 理由

- 版本更新，简历上更亮眼

### 代价与风险 ⚠️

这是**全部决策中风险最高的一条**：

- 技术新 → 教程与版本严重错配，**排错成本显著高于稳妥路线**
- 已核实的破坏性变更（详见架构文档 §2.2）：
  - **Gateway 坐标改名**：`spring-cloud-starter-gateway` → `spring-cloud-starter-gateway-server-webflux`
  - **Nacos 3.0 控制台端口独立**到 `8080`（不再是 `8848/nacos`），导致网关等服务的端口分配需避让
  - **springdoc-openapi 必须用 2.x**（3.x 是给 Spring Boot 4 的）
  - **MyBatis-Plus 3.5.9+ 分页插件依赖拆分**，需额外引入 `mybatis-plus-jsqlparser`
- **一旦卡在环境配置阶段，烂尾风险显著高于稳妥路线**

### 缓解措施

- 架构文档 §2.2 已列出完整踩坑清单
- 第一期**不引入 MQ / ES / Sentinel**，先跑通「网关 → 服务 → Nacos」最小链路
- 严格执行分期计划，每期必须有可演示产出

## D-04 身份模型

### 背景

平台需要支持「求职者 / 雇佣方 / 后台管理员」三类身份。初始设计在 `sys_user` 表上放单一字段：

```
sys_user.user_type = SEEKER / HR / ADMIN
```

同时 `company_member` 表上又有企业维度的 `role` 字段，**HR 出现了两次，自相矛盾**。

### 可选方案

1. **单一 `user_type` 字段** —— 一个账号一种身份
2. **账号 + 全局角色 + 企业维度角色** —— 按维度拆开
3. **一类身份一张表** —— 求职者表 / HR 表 / 管理员表独立

### 决策

**选方案 2。**

| 身份 | 判定方式 | 归属维度 |
|---|---|---|
| 求职者 | 拥有 `SEEKER` 全局角色 | 平台全局 |
| 雇佣者 | 存在一条 `status=正常` 的 `company_member` 记录 | **企业维度** |
| 管理员 | 拥有 `PLATFORM_ADMIN` 全局角色 | 平台内部 |

### 理由

- **三个身份不在同一维度**：求职者是相对平台的全局身份，雇佣者是**相对某家企业**的身份，管理员是平台内部人员
- 方案 1 会锁死两个真实场景：
  - ① 一个人**既是求职者又是 HR**（HR 自己也找工作，很常见）
  - ② 一个人在**多家公司任职**（A 公司 HR + B 公司 Owner）
- 「雇佣者」本质是"拥有至少一条正常的企业成员记录"，**不需要在账号上加字段**
- 企业成员离职/被移除时，雇佣者身份**自动消失**，不必回改账号表

### 代价与风险

- 查询"我有哪些身份"需要 JOIN 角色表与企业成员表
- 权限判定分两层（全局角色 + 企业角色），实现时容易漏掉企业层校验

### 面试价值

权限建模能力。能讲清"身份不应该是一个枚举字段，而是不同维度的关系"，是很强的加分点。

## D-05 是否要后台管理员

### 背景

是否需要在求职者、雇佣方之外，再加一个平台管理员身份。

### 可选方案

1. **不加** —— 只有求职者和雇佣者
2. **加**，管理员与普通账号同表，用全局角色区分
3. **加**，且管理员**独立表 + 独立登录入口**，与 C 端账号物理隔离

### 决策

**选方案 2（轻量加）。**

### 理由

- **决定性理由**：已设计 `company.verify_status`（企业资质认证），但**没有审核方** → 该字段永远停在"待审核"，企业永远发不了职位，**业务不闭环**
- 招聘平台本质上必须有审核能力：企业资质、职位合规（虚假招聘/违规岗位）、投诉处理
- 个人项目不必做后台管理前端，**几个接口即可**
- 不选方案 3 是因为成本高于收益，但**方案 3 更安全**，面试可主动提及作为"生产环境会怎么做"

### 必备安全约束 ⚠️

```
1. 注册接口硬编码只创建 SEEKER，忽略客户端传入的任何角色字段
2. PLATFORM_ADMIN 只能由数据库初始化脚本产生
```

不做这两点就是**经典提权漏洞**：

```
POST /api/auth/register
{ "username": "attacker", "userType": "ADMIN" }    ← 直接提权成管理员
```

### 面试价值

RBAC 模型、垂直越权防护、操作审计日志（`sys_operation_log`）。

## D-06 身份切换方案

### 背景

用户可能同时是求职者和招聘者，需要在两种身份间切换。

### 可选方案

1. **无状态**：请求头带 `X-Company-Id`，后端每次校验归属
2. **有状态**：`POST /switch-identity` 把当前身份写入 Redis
3. **两者都要**：查询接口 + 可选的切换接口

### 决策

**选方案 1（无状态）。**

### 理由

- **API 层面本来就没有歧义**：`/delivery/mine` 是求职者行为、`/delivery/received` 是 HR 行为，**接口语义本身已经表达了身份**
- 有状态会**多端互相覆盖**：手机上切到 HR 视角、电脑上切回求职者，服务端只存单值会被互踩
- 有状态等于放弃 JWT 的无状态前提，**退回 session 模式**
- 切换接口是**新的提权面**：典型漏洞是只校验"该用户有 `company_member` 记录"，却**没校验 `companyId` 归属**，于是能切进别人企业的身份
- 权限判定应基于**能力**（这个用户是不是企业 X 的 HR），而不是**状态**（当前是否处于雇佣者模式）

### 落地设计

```
GET /api/auth/me/identities        # 唯一身份相关接口，只读、幂等
→ {
    "globalRoles": ["SEEKER"],
    "companies": [
      { "companyId": 1, "companyName": "XX科技", "role": "HR",    "verifyStatus": "通过" },
      { "companyId": 2, "companyName": "YY网络", "role": "OWNER", "verifyStatus": "通过" }
    ]
  }
```

- 前端靠它渲染身份切换器；**切换只改前端路由和请求头，不调后端**
- 身份体现在 **URL 路由**（`/seeker/**` vs `/recruiter/**`），而不是存一个"当前身份"变量——这样刷新、分享链接、多标签都天然正确
- 企业上下文用 `X-Company-Id`，后端**每次校验**：`company_member` 存在 AND `status=正常` AND `user_id=当前用户`
- 校验结果缓存 Redis（`member:{userId}:{companyId}`），**成员变更/离职时主动失效**

### 代价与风险

- 每个企业身份接口都要做归属校验，**漏一个就是水平越权**
- 多企业任职时前端必须正确传递 `X-Company-Id`

### 例外

若同一接口需要按身份产生不同行为（典型是站内消息：你以求职者身份联系 HR，还是以 HR 身份回复求职者），带 `X-Company-Id` 即可区分，**仍然不需要服务端切换**。

## D-07 管理端接口归属

### 背景

D-05 决定引入管理员后，管理端接口放在哪里。

### 可选方案

1. **拆独立 `admin` 服务** —— 第 9 个可启动服务
2. **分散到所属服务**，用 `/admin/` 子路径区分

### 决策

**选方案 2。**

### 理由

- 管理员是**权限**，不是业务领域
- 审核企业属于 `company` 领域、下架职位属于 `job` 领域，**放在所属服务才符合边界划分**
- 为管理端拆第 9 个服务反而**破坏服务边界**，还要跨服务查询各自的数据
- 网关路由规则保持不变（仍按服务前缀路由）

### 落地形式

```
company 服务   POST /api/company/admin/{id}/verify      审核企业（通过/驳回）
               GET  /api/company/admin/company/list     待审核企业列表
job 服务       PUT  /api/job/admin/{id}/offline         下架违规职位
               GET  /api/job/admin/statistics           职位维度统计
auth 服务      GET  /api/auth/admin/operation-log       审计日志查询
```

统一加 `@PreAuthorize("hasRole('PLATFORM_ADMIN')")`。

## D-09 MySQL→ES 数据同步

### 背景

职位搜索用 Elasticsearch，需要决定 MySQL 的数据如何进入 ES。

### 可选方案

1. **代码双写** —— 写完 MySQL 紧接着写 ES
2. **Canal 监听 binlog** —— 业务无侵入，实时同步
3. **MQ 异步同步 + 定时对账** —— 业务发 MQ，消费者写 ES，另有对账任务兜底

### 决策

**选方案 3。**

### 理由

- 方案 1 **必须排除**：一旦 ES 写失败或进程崩溃，数据就**永久不一致且无法察觉**
- 方案 2 更实时可靠、对业务无侵入，是**生产环境更主流**的选择；但需要额外部署 Canal Server、处理 DDL 变更与位点管理，成本偏高
- 方案 3 能在**可控成本**下把"一致性问题"和"补偿机制"讲清楚

### 代价与风险

- 实时性弱于 Canal，存在短暂不一致窗口，靠对账收敛
- 对账任务本身要考虑性能（全量比对 vs 增量比对）

### 面试价值

被问「为什么不用 Canal」有明确答案，且能对比三种方案的取舍。**这是很好的加分题。**

## D-10 定时与延迟任务

### 背景

面试提醒（面试前 30 分钟 / 1 天）、职位过期自动下架需要定时或延迟能力。

### 可选方案

1. **XXL-Job** —— 分布式调度平台
2. **RabbitMQ 延迟消息** —— TTL + 死信队列，或延迟插件
3. **Spring `@Scheduled`** —— 单机定时

### 决策

**一期选方案 2。**

### 理由

- 延迟消息**天然适配**"面试前 30 分钟提醒"这类场景
- 避免为单一场景引入额外的分布式调度组件（降低复杂度与运维成本）
- 项目中已经在使用 RabbitMQ，复用现有中间件

### 代价与风险

- 延迟插件需额外安装（可用 TTL + DLX 规避）
- 复杂调度能力（分片、可视化、任务依赖）弱于 XXL-Job

### 后续

若二期需要复杂调度能力，再评估引入 XXL-Job。

## D-11 实时通话

### 背景

未来可能增加实时通话功能。

### 可选方案

1. **WebRTC** —— WebSocket 做信令 + STUN/TURN 做穿透
2. **WebSocket 站内实时消息** —— 在线状态、已读回执、新消息推送
3. **暂缓**

### 决策

**先做方案 2，暂缓方案 1。**

### 理由

- WebRTC 需要信令服务器 + STUN/TURN（coturn）+ HTTPS（`getUserMedia` 要求安全上下文），**成本极高**
- 面试追问 NAT 穿透、SDP 协商、丢包对抗时**很难接住**
- 而 WebSocket 站内消息可以讲「**多实例部署下长连接消息路由**」——这是很好的面试题，且性价比高

### 多实例长连接消息路由（面试点）

> 用户 A 的长连接在实例 1，消息却由实例 2 消费到，怎么推给 A？

方案：Redis Pub/Sub 广播（各实例订阅同一 channel，收到后检查本地是否有该用户连接）或 MQ 按实例维度路由。另需考虑心跳保活、断线重连、单机连接数上限。

## D-13 数据库边界

### 背景

## D-14 招聘者门槛

### 背景

平台定位为「企业招聘」。需要明确：是否允许**个人**（不挂靠任何企业）发布职位？

### 可选方案

1. **允许个人发布** —— 个人身份即可发职位（家教、兼职类平台的模式）
2. **只允许企业招聘者** —— 必须以"某公司的 HR"身份发布，个人不能以"我"的名义发（BOSS 直聘模式）
3. **两者都支持** —— 用发布主体类型区分

### 决策

**选方案 2。**

### 理由

- 平台定位聚焦企业招聘，个人发布会让**职位质量与责任主体模糊**
- 有明确的责任主体（企业）才能做**资质审核与纠纷追溯**
- 简化数据模型：`job.company_id` 可设为 `NOT NULL`，**不存在"无归属职位"这种数据**

### 代价与风险

- 求职者不能自助发职位，所有发布都依赖企业入驻流程
- 企业入驻有审核成本，**冷启动慢**

### 面试价值

能讲清"为什么不做个人发布"——责任主体与合规追溯，是产品判断与架构设计结合的体现。

## D-15 发职位门槛

### 背景

D-14 确定只允许企业招聘者。那么**企业认证状态**与"能否发职位"如何联动？

### 可选方案

1. **严格** —— 企业认证通过后才允许创建职位
2. **分层** —— 企业创建后可建职位**草稿**，但只有企业认证通过后职位才能**上线**
3. **宽松** —— 注册即可发布，认证仅作为信任标识

### 决策

**选方案 2。**

### 理由

- 保证合规底线：**对外可见（上线）的职位必然来自已认证企业**
- 不阻塞企业录入职位数据，演示与试用流程顺畅
- 方案 3 会让"企业认证"**失去业务价值**——认证若不卡住任何动作，就没有存在意义

### 落地设计

```
企业 status = 待认证   → 可建职位（草稿），不可上线
企业 status = 已认证   → 职位可上线（招聘中）
企业认证被撤销 / 注销  → 已上线职位批量下线 + 通知 HR
```

> ⚠️ 最后一条是**易漏项**：认证状态变更必须**联动职位状态**，否则会出现"企业已注销、职位仍挂线"。

### 代价与风险

- 职位状态机多一层前置校验（**创建**与**上线**是两个独立动作）
- 需要一个状态联动机制（企业认证变更事件 → 下线该企业职位）

## D-16 实名认证与归属认证的边界

### 背景

HR 身份认证 = **实名认证** + **归属认证**。这两者应该放在同一层吗？

### 可选方案

1. **合并放在 `company_member`** —— 成员表上记录"已实名 + 已归属"
2. **按维度拆开** —— 实名放 `auth`（人维度），归属放 `company`（关系维度）

### 决策

**选方案 2。**

### 理由

- **实名是"人"的属性，归属是"关系"的属性**
- 一个人在 A 公司实名后，跳槽到 B 公司**不应重新实名**
- 求职者投递时同样可能需要实名（防虚假简历），**实名能力本就不属于 company 领域**

### 落地设计

发职位 = **三重校验，缺一不可**：

```
实名通过 (auth)  AND  归属正常 (company_member)  AND  企业已认证 (company)
```

### Mock 实现要点

**身份证校验码算法（GB 11643-1999 / ISO 7064 MOD 11-2）可以真实实现**，不依赖任何外部接口：

```
格式 + 校验位     → 真实算法校验（能识别伪造号）
姓名与号是否一致   → mock（需要公安接口，个人项目不可得）
```

抽成策略接口，生产环境换实现类：

```java
public interface RealNameVerifier { RealNameResult verify(String name, String idCard); }
// MockRealNameVerifier        开发默认：真算法 + 模拟人证比对
// ThirdPartyRealNameVerifier  生产：接三方实名核验 API
```

### 面试价值

> "我的 mock 不是直接返回 true，而是**真实实现了身份证校验位算法**，只有'人证一致'这一步是模拟的。"

## D-17 法定代表人定位

### 背景

企业侧是否需要区分「法定代表人」与「普通 HR」？法人是否应拥有更高权限？

### 可选方案

1. **不区分** —— 只保留 `OWNER / HR`
2. **仅作标记 + 管理员兜底** —— 法人是标记字段，不作为权限开关
3. **法人拥有高于 OWNER 的权限** —— 如可强制转移所有权

### 决策

**选方案 2。**

### 理由

- **法律身份 ≠ 平台权限**：法人可能是挂名的；大公司的法定代表人通常**不是实际管理者**
- 若给法人天然全权限，会出现**权限冲突**或"账号无人能管"
- 但法人信息有真实价值：**OWNER 离职且无人接管时，法人可凭实名信息向平台申请接管**（走管理员人工处理，见下）

### 落地设计

| 字段 | 来源 | 性质 |
|---|---|---|
| `company.legal_person_name` | 工商数据（企业认证时返回） | 记录 |
| `company_member.is_legal_rep` | 实名姓名与法人姓名匹配 | **标记，不是权限开关** |

平台权限**仍由 OWNER 体系决定**。

### 衍生需求：OWNER 缺失怎么办

创建者离职后，企业账号由谁管理？

**决策：不建专门机制，由平台管理员人工介入。**

- `company.owner_id` 与 `company_member.role = 'OWNER'` 是**重复表达**，双数据源必然出现"改了角色却忘了改 owner_id"的不一致
- 转移接口的边界情况多（OWNER 唯一性、原子性、接收方必须是本企业成员、不能转给自己），**成本高于收益**
- **面试几乎不会问"所有权转移"**；它想体现的「权限变更原子性与缓存一致性」，在"调整角色 / 移除 HR"这些基础操作里**同样能体现**
- 更换 OWNER 直接复用**已有的管理端接口**（管理员改角色），零额外设计成本

**因此**：

- OWNER 的**唯一数据源** = `company_member.role = 'OWNER'`（**不设 `company.owner_id`**）
- 一期只需保证「创建者自动成为 OWNER」且「至少有一人是 OWNER」（应用层约束）

### 面试价值

能清晰区分「法律身份」与「产品权限」，体现建模成熟度。

## D-18 企业认证数据源

### 背景

需要鉴别企业是否为**有效实体**（经营状态：存续 / 注销 / 吊销）。

### 可选方案

1. **爬取第三方网站**（天眼查 / 企查查等）
2. **接入有授权的付费工商数据 API**
3. **纯人工审核**（上传营业执照，管理员目视）

### 决策

**选方案 2：接入阿里云市场的工商数据 API**（有免费额度，可先用免费额度验证）。
同时**保留 Mock 实现**作为开发默认与**降级兜底**（接口可切换）。

### 理由

- **方案 1 必须排除（法律风险）** ⚠️：
  - 违反目标网站用户协议
  - 可能构成《反不正当竞争法》下的不正当竞争
  - **绕过反爬措施可能触及《刑法》第 285 条**
  - **面试负分**：大厂面试官听到"我爬了天眼查的数据"会直接质疑合规意识，**这比技术问题严重得多**
- 方案 3 不可扩展，且**无法自动识别"注销 / 吊销"**
- 阿里云市场有现成服务，且比预想的更对口（**含免费额度，可先验证**）：
  - **企业三要素校验**（企业名称 + 法人姓名 + 统一社会信用代码 一致性核验）
  - 企业工商信息信用核验服务 / 营业执照信息校验

### 落地设计

```java
public interface CompanyVerifier { CompanyVerifyResult verify(CompanyVerifyRequest req); }
// MockCompanyVerifier    开发默认 + 降级兜底：本地模拟工商库
// AliyunCompanyVerifier  正式实现：走阿里云市场 API
```

**接口切换用配置开关**（`hirehub.verify.channel = MOCK | ALIYUN`）。

> ⚠️ **两个接入注意**：
> 1. **免费额度有限**（按次 / 按天）。额度耗尽接口会失败 → 因此 **Mock 兜底必须保留**，不能因为接了真 API 就删掉，否则演示当天可能翻车
> 2. **AppCode 绝不能进 Git**。阿里云市场 API 通常用 Header 中的 `AppCode` 鉴权 → 走**环境变量**注入，并把本地配置文件加入 `.gitignore`

**统一社会信用代码校验码算法（GB 32100-2015，mod 31）同样可以真实实现**，因此 Mock 能做到"格式真校验 + 数据源模拟"，而不是无脑放行。

### 关键建模点

1. **企业唯一标识必须用统一社会信用代码，不能用企业名称**
   企业会改名，且相似名称极多（"XX科技有限公司" vs "XX网络科技有限公司"）——用名称判重会导致同一家公司**重复注册**。
2. **认证结果为"存续"才通过**，注销 / 吊销 / 经营异常必须拒绝。
3. **认证记录必须留档**（`company_verify_record`）：提交材料、第三方返回原文、审核人、结果、时间。
   企业认证是**有法律后果的操作**，必须可追溯——与 `sys_operation_log` 同一思路。
4. **营业执照与身份证号是敏感个人信息**，需**加密存储 + 日志脱敏**（《个人信息保护法》要求）。

### 代价与风险

- 真实 API 按次收费（**免费额度有限**），需要配额控制与失败降级策略
- 认证存在**时效性**：企业后续可能注销 → 理想做法是定期复核（可作为加分项，一期可不做）

### 面试价值

合规意识 + 接口抽象能力。主动指出"爬取有法律风险，我会走授权 API"是很强的加分点。

## D-19 企业成员加入方式

### 背景

企业创建后（创建者自动成为 OWNER），其他 HR 如何加入企业？

### 可选方案

1. **邀请码直接加入** —— OWNER 生成邀请码，HR 凭码直接成为成员
2. **申请 + OWNER 审批** —— HR 提交申请，OWNER 审核通过后才成为成员
3. **仅单个账号** —— 企业只有创建者一个账号，不做多成员

### 决策

**选方案 1（邀请码直接加入）。**

### 理由

- 方案 3 不可行：多 HR 协作是招聘平台的常见场景，只有单账号演示不了
- 方案 1 比方案 2 **少 2 个接口、少一套申请状态机**，演示流程也更短
- 方案 2 的面试价值中等（审批流本身不是技术难点），**不值得为此增加复杂度**
- 安全性可接受：邀请码本身即凭证，配合有效期即可

### 落地设计

最简实现，**不建独立邀请码表**：

```
company.invite_code              随机字符串（唯一）
company.invite_code_expire_time  有效期

凭码加入 → 校验 code 匹配且未过期 → 创建 company_member(role = HR)
```

接口：

```
POST /api/company/{id}/invite-code   生成 / 重置邀请码（仅 OWNER）
POST /api/company/join               凭 code 加入
```

### 代价与风险

- 无法追溯"谁生成过哪些码、用过几次"，也**不能单独撤销某一次邀请**
- 若后续需要"一码一用 / 可撤销 / 可审计"，再升级为独立的 `company_invite_code` 表

### 面试价值

能说明"为什么这里不做审批流"——**权衡的不是能不能做，而是值不值得做**。

## D-20 平台不预置企业数据

### 背景

平台上是否应该出现「没有招聘者的企业」？

也就是说：要不要建立企业库，从第三方工商数据批量收录企业，让求职者能浏览那些没人在平台上招人的公司主页？

### 可选方案

1. **平台预置企业库** —— 从工商数据批量收录，企业主页先有页面、后由企业「认领」
2. **企业信息完全随入驻产生** —— 只有人创建企业并通过核验后，平台上才有这家企业
3. **一张表 + `source` 字段** —— 区分「平台收录」与「用户创建」

### 决策

**选方案 2。**

### 理由

**1. 工商数据里没有求职者关心的信息**

| 第三方能提供 | 求职者想看的 |
|---|---|
| 企业名称、统一社会信用代码 | 实际办公地点 |
| 法定代表人、注册资本 | 团队规模、技术栈、业务方向 |
| 注册地址、成立日期 | 薪资水平、福利、加班情况 |
| 经营状态 | 面试流程、真实评价 |

两者**几乎不重叠**——注册地址常常和实际办公地不是一处；注册资本、法定代表人是谁，对求职者都没有参考价值。

**预置出来的企业主页信息量极低，且大概率误导。** 一个既不可靠又没有价值的信息页面，展示它的意义是什么？

**2. 合规与责任风险**

- 未经企业确认就展示其名称、Logo 从事商业展示，本身存在争议（企业有权要求下架）
- 更麻烦的是**责任边界**：求职者基于平台展示的信息做决策，如果信息过时（已搬迁 / 已注销 / 规模严重缩水），这个误导责任由谁承担？
- 平台**无法保证**预置数据的准确性，也就不该展示它

**3. 会稀释核心机制的价值**

本平台的企业信息都经过工商核验 + 法人授权 / 人工审核。若混入大量从未被任何企业确认过的预置数据，会削弱**「企业信息全量可信」**这个优势。平台上每条企业信息都可信，本身就是竞争力。

### 代价与风险

- 求职者**无法浏览"当前没有招聘需求"的公司主页**——平台上只存在有招聘者的企业
- 企业数量增长完全依赖入驻，**冷启动慢**

### 边界（仍需保留）⚠️

不预置 ≠ 不关心企业经营状态。对**已入驻**企业仍须保证其状态有效：

```
企业认证时        → 第三方返回 business_status；注销 / 吊销 / 经营异常 → 不通过
入驻后被注销      → 定期复核发现 → 认证置为「已撤销」
                  → 该企业已上线职位【批量下线】+ 通知 HR
```

即：我们**不主动收录企业**，但对平台上已入驻的企业，有责任保证其状态仍然有效（见 Q-08）。

### 面试价值

"为什么不做企业库"是一道能同时体现**产品判断**与**合规意识**的题。答得好比"我从工商库同步了企业信息"更像想清楚过。

## D-21 企业内职位权限边界

### 背景

同一家企业下可能有多个招聘者（OWNER + 若干 HR）。`job` 表有 `publisher_id` 记录发布者，但**它的权限语义从未定义**：

> HR A 能不能修改 / 下架 HR B 发布的职位？

### 可选方案

1. **企业级共享** —— 所有 OWNER/HR 都能操作全部职位，无差别
2. **发布者 + OWNER** —— HR 只能操作自己发布的，OWNER 管全部
3. **企业级共享 + 删除收敛给 OWNER** —— 常规操作共享，高风险操作仅 OWNER

### 决策

**选方案 3。**

### 理由

- 招聘团队通常就 2–5 个 HR 协作，**互相代班是常态**，企业级共享符合实际
- 方案 2 的问题是：**HR 离职后他发布的职位无人能管**，除非 OWNER 逐个接管
- 但**删除不可逆**，属于高风险操作，应收敛到 OWNER
- 更重要的是：**如果 OWNER 和 HR 在 job 领域权限完全一样，这两个角色凭什么区分？**
  把删除收敛给 OWNER，正好让角色差异有了实际意义（配合 D-19 的"生成邀请码仅 OWNER"）

### 落地设计

| 操作 | 企业角色 | 额外前置 |
|---|---|---|
| 创建草稿 / 修改 | OWNER / HR | 实名 |
| 上线 | OWNER / HR | 实名 + **企业已认证** |
| 下线 | OWNER / HR | 实名（企业认证失效时也允许） |
| **删除** | **仅 OWNER** | 实名 |
| 下架违规职位 | PLATFORM_ADMIN | — |

**两点务必注意**：

- job 领域的权限**只看企业维度角色**，与全局角色（`SEEKER`）无关
- 企业角色只是**三个条件之一**——实名、归属、企业认证缺一不可

### 代价与风险

- HR 无法删除自己发布错的职位，需 OWNER 协助
- 企业级共享意味着任何 HR 都能改动同事的职位，依赖团队内部信任

### 面试价值

能说明"角色划分不是摆设"——**每个角色都要有独占的操作，否则就是多余的抽象**。

## D-22 统一搜索的索引结构

### 背景

求职者既会搜**岗位名**（"Java 工程师"），也会搜**公司名**（"某某科技"）。搜索入口是统一的，但底层索引怎么组织？

### 可选方案

1. **两个索引** —— `job_index` / `company_index` 分开，分别查询后按类型分组返回
2. **单索引 + `type` 字段** —— 职位与公司文档放同一索引，用 `type` 区分
3. **只做职位搜索** —— 不支持搜公司

### 决策

**选方案 1。**

### 理由

- 两类文档**字段差异极大**：公司看行业 / 规模 / 城市 / 在招职位数；职位看技能 / 薪资 / 经验 / 学历
- 更关键的是**相关性评分量纲不同**——把"Java 工程师"和"某某科技公司"混在一个列表里排序，得到的结果**没有意义**，用户也无法理解"为什么这家公司排在那个职位前面"
- 分开后各自建模、各自评分，逻辑清晰

### 落地设计

```
GET /api/job/search?keyword=Java      → job_index
GET /api/company/search?keyword=Java  → company_index
前端在同一搜索框下并行调用，分 Tab 展示
```

> 与 §6.1「`/me/identities` 前端分别调用、auth 不聚合」是同一个原则：
> **跨领域的聚合放在前端，不制造服务间的强依赖。**

**边界**：公司**无在招职位时仍可被搜到**，标注「暂无在招职位」。公司主页本身对求职者有价值，且与 D-20「企业随入驻产生」一致。

### 代价与风险

- 前端要发两次请求（可并行，感知差异小）
- 跨类型的统一排序不可得（**也不需要**——混排本身就是错的）

### 面试价值

"为什么不混排"能体现对**相关性评分**的理解，而不是只会调 ES API。

## D-23 求职者隐私模型

### 背景

设想做一个「岗位偏好」功能：既能定期给求职者推送匹配职位，也能把简历暴露给有需求的 HR。

第二件事涉及个人信息（姓名、手机号、邮箱、工作经历），需要决定暴露策略。

### 可选方案

1. **简单的「公开 / 保密」开关** —— 用户自己决定开不开
2. **求职状态 + 多层隐私控制** —— 状态驱动可见性，并叠加匿名化等手段
3. **不做曝光** —— 只做正向推送

### 决策

**选方案 2。**

### 理由

- 方案 1 **太粗**：真实场景中"在职找工作"的人最怕被**现在的公司**看到。一个"公开"按钮解决不了——他既想被别的 HR 发现，又不想被现公司发现
- 多层控制才能同时满足"被 HR 发现"与"隐私安全"两个诉求
- 方案 3 放弃了「人才库」这个招聘平台的核心价值面

### 落地设计

**核心原则：默认最小可见，由用户主动放开。**

```
可被 HR 搜到  ⟺  job_status ∈ {随时到岗, 考虑机会}  AND  简历 status = 公开
```

| 层 | 作用 |
|---|---|
| **求职状态** | 离职-随时到岗 / 在职-考虑机会 → 可被搜到；**在职-暂不考虑 → 完全不出现** |
| **匿名化** | HR 默认只看到"张先生 / 5 年经验 / 某互联网公司"，**看不到姓名与联系方式** |
| **联系方式需同意** | HR 发起沟通、**用户同意后**才展示真实信息 |
| **屏蔽公司** ⭐ | 不让自己现在的公司搜到（在职找工作必备） |
| **可见范围** | 只有**已认证企业的 HR** 能搜人才库，且每次查看**留痕** |

**为什么"屏蔽公司"值得单独做**：成本极低（一个 JSON 字段 + 一个 filter），但它解决的是在职求职者**最真实的恐惧**。

### 与 D-20 的关系

同一原则的两面：

- D-20：**未经企业确认，不展示企业信息**
- D-23：**未经用户明确同意，不展示其个人信息**

### 代价与风险

- 需要维护 `resume_index`，且**隐私状态变化必须实时生效**（关闭曝光要立即从索引删除），不能像职位索引那样依赖对账任务收敛
- 匿名化后 HR 的筛选体验下降，沟通转化率可能变低（这是隐私的必然代价）

### 面试价值

隐私合规 + 产品思维。**"默认最小可见"是数据产品设计的通行原则**，能讲出来说明不是只会写 CRUD。

## D-24 招聘者三层核验模型

### 背景

招聘者要代表企业发布职位，必须先证明自己"有资格代表这家企业"。
原设计只有「提交认证 → 管理员人工审核」一条简链路，缺乏对企业冒名注册的防御。

### 可选方案

1. **单层人工审核** —— 上传营业执照，管理员目视通过
2. **三层核验（借鉴 BOSS 直聘）** —— 个人实名 / 企业归属 / 法人强验证
3. **两层（实名 + 材料人工审核）** —— 不做法人授权

### 决策

**选方案 2：三层核验。**

| 层 | 确认什么 | 实现 | 归属服务 |
|---|---|---|---|
| 一 个人实名 | "你是谁" | 姓名 + 身份证（校验位**真算法**）+ 人脸核身 Mock | **auth** |
| 二 企业归属 | "你代表谁" | **风险评分** → 要求材料（邮箱 / 在职证明 / 授权书） | company |
| 三 法人强验证 | "公司同意你招人" | **法人授权令牌闭环** | company |

### 关键洞察：第三层的本质是"法人主动授权"，不是"姓名比对"

查工商数据得到法人姓名，**唯一作用是知道该找谁授权**。真正的验证来自**法人本人**完成实名并点击同意——这是**强证据**。

- 若靠「申请人姓名 == 法人姓名」来授权，是**弱证据**：中文重名率极高，任何人只要和法人同名就能冒名接管企业
- 法人主动授权则**彻底消除重名问题**——授权来自法人本人行为，不是系统推断

### 第三层落地：法人授权令牌闭环

```
① 申请人提交企业认证 → 查第三方得到法人姓名
② 生成授权令牌（随机、一次性、有有效期）
③ 把授权链接发给法人（邮件 / 短信）
④ 法人打开链接 —— ⚠️ 无需注册账号
⑤ 法人填写姓名 + 身份证（人脸 Mock）完成实名
⑥ 法人确认授权 → company_authorization.status = 已授权
⑦ 申请人获得该企业招聘权限
```

**安全要点**：令牌足够随机（防猜测）、一次性 + 有效期、**法人必须完成实名才能授权**（不是点一下就算）、授权可撤销、全程留档。

> 法人授权后，`is_legal_rep` 由**法人本人完成授权**这一行为得出（强证据），而非姓名匹配。

### 第二层：风险评分（简单加权，不引规则引擎框架）

先算风险等级，再决定要什么材料：

| 维度 | 加分 | 减分 |
|---|---|---|
| 工商经营状态 | 存续 | 注销 / 吊销 → **直接拒** |
| 申请人实名 | 已认证 | 未认证 |
| 邮箱域名 | 企业域名 | 免费邮箱（qq/163） |
| 材料完整度 | 有授权书 / 在职证明 | 缺 |
| 企业成立年限 | ≥ 3 年 | < 1 年 |
| 历史记录 | 首次申请 | 同企业曾被驳回 |

```
低风险      → 材料齐全 + 企业邮箱验证 → 自动通过
中 / 高风险  → 法人授权 或 人工审核
```

### 代价与风险

- 核验链路长，企业入驻流程重，**冷启动更慢**
- 法人授权依赖法人本人配合，不配合则卡在第三层，需人工兜底
- 各层 Mock 边界必须讲清：人脸核身 Mock、企业数据走阿里云市场

### 面试价值

「你凭什么相信申请人是这家公司的？」——三层核验是这道题的完整答案，且每层职责边界清晰。

## D-25 面试官不设独立角色

### 背景

原设计 `company_member.role = OWNER / HR / INTERVIEWER`，把「面试官」做成了企业成员的固定角色。

### 可选方案

1. **固定角色** —— 成员表加 `INTERVIEWER`
2. **按面试实例授权** —— `interview.interviewer_id` 指定谁面
3. **本期不建模** —— 只有 `OWNER / HR`，面试反馈由 HR 代录

### 决策

**选方案 3。**

### 理由

- 面试官本质是**按面试实例**授权的：同一个人可能只面 A 岗位、不面 B 岗位。
  固定角色表达不了"只面某几场"，会导致**越权看到全部候选人**
- 方案 2 更准确（`interviewer_id` 本就要存），但本期直接**简化为 HR 代录反馈**，
  面试官姓名以 `interview.interviewer_name` 文本留痕——成本最低
- 若未来要"业务部门自助提交面试反馈"，再升级到方案 2，**不推翻本期设计**

### 代价与风险

- 业务部门（面试官）不能自助录入反馈，需 HR 转述
- `interviewer_name` 是自由文本，无法关联账号、无权限约束

### 面试价值

能说明"角色不是越多越好"——**按实例授权 vs 固定角色**的取舍，以及"本期简化的边界在哪"。

## D-26 投递简历快照

### 背景

用户投递简历后可能修改简历。HR 查看历史投递时，应该看到**投递那一刻的简历**，还是**最新简历**？

### 可选方案

1. **只存 `resume_id`（引用）** —— HR 实时 join，看到最新简历
2. **存简历快照** —— 投递那一刻复制一份，HR 看到投递时的版本
3. **简历版本管理** —— 简历表做版本，投递存 `(resume_id, version)`

### 决策

**选方案 2。**

### 理由

- **投递是"时间点"事件**：投递那一刻的简历是那一刻的"要约材料"，事后修改**不应追溯改变历史**
- 只存引用（方案 1）有三个问题：
  - HR 看历史投递看到的是"会变的历史"，与当初筛的对不上
  - HR 因"3 年经验"拒绝某人后，对方改成"5 年经验"，**拒绝的依据就消失了**
  - 用户删除简历后，历史投递**断链**
- 方案 3 需要版本表 + 版本递增 + diff 管理，成本高——**快照已经承载历史，简历表只存当前版本即可**

### 落地设计

```
delivery.resume_id         引用 —— 保留，作为"查看最新简历"的入口
delivery_resume.snapshot   JSON —— 投递那一刻的简历全文

HR 查看历史投递    → 展示快照（投递那一刻的版本）
HR 点"查看最新简历" → 走 resume_id 查当前简历
```

- 快照放**独立表** `delivery_resume`：`delivery` 主表高频读写不背大 JSON；列表页不碰快照，只有详情页才读
- 快照在**投递的本地事务内**一起写入（与 `delivery`、`local_message` 同事务），保证投递成功 ⟺ 快照落库
- 附件文件本身不复制，快照只存"投递时用的附件 ID"

### 与"多份简历"的关系

一个用户可有多份简历（`resume.user_id` 多行，一份为默认）。投递记录里的 `resume_id` 指向**投递时选用的那一份**，快照也是那一份。

### 面试价值

必考级。标准答案：

> "投递存快照，不存引用——投递是时间点事件，事后改简历不该追溯影响历史；且快照独立于简历生命周期，简历删了投递也不断链。"

## D-27 投递状态机

### 背景

投递（delivery）是平台唯一真正的"状态机"，从投递到入职经历多阶段流转。若用 if/else 表达状态迁移，会迅速变成一团难以维护的分支。

### 可选方案

1. **if/else 判断** —— 在 service 里手写分支判断当前状态
2. **Spring Statemachine** —— 引入状态机框架
3. **事件驱动 + 迁移表** —— 自建轻量状态机（枚举 + 迁移表）

### 决策

**选方案 3。**

### 理由

- 方案 1 是"目标状态驱动"：调用方说"改成 OFFER"，代码里写一堆 if。新增迁移、改权限、加状态都要改判断代码，**必然失控**
- 方案 2 功能全但**太重**，个人项目不值，且是"框架黑盒"——面试时讲不清自己到底做了什么
- 方案 3 成本极低（一个枚举 + 一张迁移表 + 一个 transition 方法），原理透明

### 落地设计

**状态（8 个，终态 3 个）**：
`PENDING / VIEWED / COMMUNICATING / INTERVIEW / OFFER / HIRED / REJECTED / CANCELLED`

> **`VIEWED` 是"观察标记"而非"流程节点"**：它只记录"HR 看过但未行动"，不改变流程走向
> （`PENDING` 与 `VIEWED` 的后续合法迁移完全一致）。保留它，是为了让投递列表能区分"未看 / 已看"。

**职责边界**：`REJECTED` = **HR 终止**（不合适 / 面试不过 / 撤回）；`CANCELLED` = **求职者终止**（撤销 / 放弃 / 拒 Offer）。

**三个原则**：

1. **事件驱动** —— 调用方发起事件（`SEND_OFFER`），不是指定目标状态
2. **迁移表驱动** —— 合法迁移存 `Map<Status, Set<Event>>`，迁移 = 查表
3. **权限绑定在事件上** —— `CANCEL` 只能求职者本人，`REJECT / SEND_OFFER / HIRE` 只能 HR

> **事件是唯一写入口**：前端只发事件、不传目标状态；`status` 对前端只读，只能由状态机派生。
> `VIEW` 事件由 `GET /deliveries/{id}`（HR 打开详情）自动触发，前端不显式发。

```java
void transition(delivery, event, actor) {
    1. 校验事件在该状态下合法      // 查 transitions
    2. 校验 actor 有权限发起该事件  // 查 actorRules
    3. 乐观锁 UPDATE ... WHERE status = 前态
}
```

**并发**：乐观锁（`WHERE status = 前态`），affected rows = 0 即迁移失败。

> **状态迁移成功后，在同一本地事务里写通知消息**（`local_message.biz_type = 'DELIVERY_EVENT'`），
> 保证"状态改了，通知一定发出去"（复用 D-01 机制，见 §6.2）。

### 代价与风险

- 状态与事件多了之后，迁移表本身需要维护（但比 if/else 好维护）
- **不支持终态逆迁**——误操作靠确认弹窗防，不靠状态机放开；若真要恢复，重新投递

### 面试价值

"为什么用迁移表而不是 if/else"是必考级问题，能体现对状态机与工程化的理解。

## D-28 投递与面试解耦

### 背景

一个投递可能经历多轮面试（一面 / 二面 / 终面）。面试状态与投递状态的关系如何设计？

### 可选方案

1. **面试状态写回投递状态** —— 面试完成 / 拒绝后自动流转投递
2. **投递与面试两套独立状态机** —— 1 : N 关系，面试状态不影响投递状态

### 决策

**选方案 2。**

### 理由

- **投递状态是"整体流程走到哪一步"，面试状态是"INTERVIEW 这一步内部安排了什么"**——两个层级
- 方案 1 的问题：面试反馈是 HR 的"决策依据"，不是"决策本身"。候选人可能二面通过但 HR 还想再面，或多轮通过后因薪资谈崩——自动流转会**绕过 HR 的显式决策**
- 面试取消 / 拒绝只代表"INTERVIEW 这一步内的一次尝试失败"，整体流程仍停在 INTERVIEW，HR 应可重新发起

### 落地设计

- **投递 : 面试 = 1 : N**，`interview.round` 区分轮次
- 面试状态：`SCHEDULED / CONFIRMED / COMPLETED / REJECTED / CANCELLED`（终态 3 个）
- 取消记 `cancelled_by` + `cancel_reason`；改期回 `SCHEDULED` 需重新确认
- 面试反馈**只记录不流转投递**；投递状态始终由投递事件（`SEND_OFFER` / `REJECT`）驱动
- `round` 是面试维度，**不进投递状态机**

### 面试价值

"投递状态和面试状态为什么分开"能体现对**状态层级**与**解耦**的理解；"反馈为什么不全自动流转"能体现对**人机协作边界**的判断。

## D-29 自然语言搜索

### 背景

职位搜索当前是「关键词 + 结构化过滤」（城市 / 薪资 / 学历 / 经验）。但求职者的真实输入往往是一句自然语言：

```
杭州 30k 以上 本科 Java 后端
不加班 的 远程 前端 25-40k
```

需要让用户**直接说人话**也能搜到，而不是先教他怎么填筛选器。

### 可选方案

1. **规则解析** —— 手写正则 / 词典抽取城市、薪资、学历等字段
2. **接入大模型 API** —— 把自然语言格式化成 ES 需要的结构化查询
3. **Embedding 向量检索（RAG）** —— 语义召回 + ES 过滤

### 决策

**选方案 2，模型用 qwen3.7-plus（通义千问，走 DashScope OpenAI 兼容接口 + JSON mode）。**

### 理由

- 自然语言搜索是招聘平台的明显亮点，能体现「LLM 应用 与 传统检索结合」的能力
- 方案 1 对歧义表达（"3 万以上""本科及以上""25-40k"）覆盖差、规则越堆越难维护
- 方案 3 成本与复杂度更高；本平台职位量级下，**结构化查询 + 关键词相关性**已足够，向量检索留作后续演进

### 落地设计

```
GET /api/job/search/nl?q=杭州 30k 以上 本科 Java 后端
  → SearchQueryParser.parse(q)
  → SearchIntent { keyword, city, salaryMin, salaryMax, education, experience }
  → 复用 JobSearchService.search(...)（现有 ES 查询逻辑，D-22 双索引中的 job_index）
```

- `SearchQueryParser` 抽成接口 + 可插拔实现（与 D-16 `RealNameVerifier`、D-18 `CompanyVerifier` **同一套模式**）：
  - `LlmSearchQueryParser`　正式实现：调通义千问 **qwen3.7-plus**（`dashscope.aliyuncs.com/compatible-mode/v1` + `response_format=json_object`），提示词约束输出 JSON（keyword + 各过滤字段）
  - **提示词与 ES 对齐**：把 `city`/`education`/`experience` 约束到 ES keyword 字段的候选值（如「杭州」不带「市」字、学历从 `不限/高中/大专/本科/硕士/博士` 选、经验从 `应届/1-3年/3-5年/5-10年/10年以上` 选），薪资统一折算为「元/月」整数——保证 LLM 输出能被 ES 的 `term`/`range` 过滤直接消费，不做同义改写
  - `MockSearchQueryParser` 开发默认 + 降级兜底：本地规则粗抽，保证无 Key/断网时功能不瘫
- 配置开关：`hirehub.search.parser = MOCK | LLM`；LLM 的 API Key 走**环境变量**，绝不进 Git（同 D-18 的 AppCode 处理）

### 关键边界（面试可能追问）

**大模型只负责「理解意图」，不负责「检索」**：它输出的仍是被字段白名单约束的结构化条件，
真正的召回与排序仍由 ES 完成（`multi_match` 相关性 + `filter` 精确过滤 + `status=1` 硬约束）。
这样既拿到了自然语言的便利，又不会因为模型幻觉把不该出现的职位放出来。

### 代价与风险

- LLM 有延迟与成本，而搜索是高频场景 → 需要结果缓存 + 超时降级到关键词搜索
- 提示词注入：用户输入直接进提示词，需把输出当「查询理解」而非「指令」，且服务端对输出的字段做白名单校验
- 模型选型未定（Q-10），因此接口设计**不绑定任何厂商**

### 面试价值

能讲清「LLM 与传统检索各司其职」比「我把搜索丢给大模型」值钱得多：
自然语言 → 结构化意图（LLM）→ 相关性 + 过滤（ES），每一段都可解释、可降级。

## D-31 简历解析管线

### 决策

**上传确认后异步解析**：`confirm-upload` → 发 `resume.parse`（MQ）→ 消费者从 MinIO 取文件 → PDFBox / POI 抽文本 → 写 `resume_parse_detail` + `resume_index` → 更新 `parse_status`。

### 关键约束

| 约束 | 内容 |
|---|---|
| **异步** | 解析耗时数百毫秒到数秒，放同步请求里会拖住上传接口吞吐并让用户等待 |
| **不覆盖用户数据** | 解析结果写独立表 `resume_parse_detail`；只回填 `resume` 的**空字段**，用户手填的是权威 |
| **失败要说清原因** | `parse_status=3` + `parse_error`（扫描件无文本层 / 加密文件 / 读取失败），并提供手动重试 |
| **坏文件不重试** | 业务性失败由消费者捕获后正常 ACK（重试解决不了坏文件，只会堵队列）；只有基础设施异常才 nack 重入队 |
| **可靠性取舍** | 不像投递那样建本地消息表：解析幂等且用户可主动重试，丢消息只导致"暂时搜不到"，不值得再建一套可靠投递 |

## D-32 面试提醒延迟消息

### 决策

RabbitMQ **TTL + DLX**（不安装延迟插件）：面试创建/改期时按提前量（1 天 / 30 分钟）投递消息，到期进死信 → 通知消费者。

### 必须承认的缺陷与缓解

消息级 TTL 存在**队头阻塞**：长 TTL 消息排在队头时，后面的短 TTL 消息要等它先死信。缓解手段是**定时兜底扫描**（每 5 分钟找"即将开始但未发提醒"的面试补发）+ `interview_reminder` 表的 `(interview_id, tier)` 唯一键去重，保证不重不漏。

> 这条取舍本身就是面试素材：**为什么不无脑上延迟插件** + **TTL 方案的坑怎么补**。

## D-33 服务内方法级鉴权

### 背景

D-02 已预警："网关鉴权模式下，下游服务需手工构建 `SecurityContext`，否则 `@PreAuthorize` 全部拒绝或全部放行。" 三期落地 D-07 时必须正面解决。

### 决策

在需要方法级鉴权的服务（company / job / auth）引入 `spring-boot-starter-security`：

1. `HeaderAuthenticationFilter`（`hirehub-common`）读网关注入的 `X-User-Id` / `X-User-Roles`，构造 `UsernamePasswordAuthenticationToken`，权限补 `ROLE_` 前缀（`hasRole('X')` 匹配 `ROLE_X`）
2. `SecurityFilterChain` **全 `permitAll`** —— 鉴权边界仍在网关，服务侧只做"基于已注入身份的方法级校验"
3. `@EnableMethodSecurity` + 各管理端接口统一 `@PreAuthorize("hasRole('PLATFORM_ADMIN')")`

### 为什么全 permitAll

不这么做，引入 Security 后**所有接口（含 `/internal/**`）会直接 401**（Boot 默认链要求认证）。这是接入时最容易踩的坑，已记入踩坑记录 #13。

### 代价与风险

- **安全前提**：服务必须只能被网关访问。若服务端口可被外部直连，攻击者伪造 `X-User-Id` 即可提权 —— 生产必须靠网络策略/安全组隔离
- `AccessDeniedException` 发生在 DispatcherServlet 内部，**到不了** Security 的 `ExceptionTranslationFilter`，会被全局异常兜底吞成 500，必须单独 `@RestControllerAdvice` 映射 403
- 多引了三个依赖（core / web / config + starter），服务启动稍慢

## D-34 WebSocket 站内消息

### 决策

**并入 `hirehub-notification`**（不新增第 9 个服务），多实例消息路由用 **Redis Pub/Sub 广播**。

### 关键设计

| 项 | 方案 | 为什么 |
|---|---|---|
| **鉴权** | 一次性 `ws-ticket`（Redis 存 60s，用完即删） | 浏览器 WebSocket API **不能自定义请求头**，只能把凭证放 URL；直接放 accessToken 会被网关/Nginx 日志记录。ticket 短时一次性把风险压到最低 |
| **多实例路由** | 消息落库后 `PUBLISH` 到 `hirehub:ws:push`，各实例订阅后只推给本地持有的连接 | 实例间不需要互相知道；对比"MQ 按实例维度路由"更简单且效果相同 |
| **离线** | 只落库，上线后走 REST 拉取 | WebSocket 不做可靠投递，避免"只推不存"导致丢消息 |
| **保活** | 服务端 30s PING / 客户端 PONG，超时断开；`onClose` 清会话表 | 半开连接不清理会持续占内存 |

### 代价与风险

- 网关需加 `/ws/**` 路由与白名单（拿不到 Authorization 头），ticket 校验下沉到 notification
- 单机连接数有上限，需限流与连接数监控

## D-35 管理端审计日志

### 决策

**集中存 auth** 的 `sys_operation_log`，业务服务（company / job）在管理操作成功后通过内部接口上报。

### 理由

- 审计的价值是"**一个管理员干了什么要能一次查全**"；分散在各服务存储就得跨库聚合，违反 D-13

- 操作人名称由 auth **本地补全**，不信任调用方传来的字符串

## D-36 中间件全容器化与 RabbitMQ 访问凭据

### 背景

二期时只有 RabbitMQ 跑在宿主机（原生 Windows 服务），其余中间件都在容器里，导致
**一份编排起不全全栈**：`docker-compose.yml` 拉的栈缺 broker，换机器要额外装一个原生 RabbitMQ。
三期收口（M5.2）要把 broker 也纳入编排。

但直接搬进容器会踩两个坑：`guest` 用户默认只允许 loopback 登录（见踩坑 #33），
以及 `RABBITMQ_DEFAULT_USER` 对已初始化的数据卷不生效（见踩坑 #34）。

### 决策

1. **RabbitMQ 纳入 `docker/docker-compose.yml`**，与 MySQL / Redis / Nacos / ES / MinIO 同一份编排，
   `docker compose -f docker/docker-compose.yml up -d` 一次拉起**全部中间件**。
   固定 `hostname: hirehub-rabbitmq`，避免容器重建后节点名变化导致数据目录不可用。
2. **使用专用非 guest 账号**（默认 `hirehub`），**不使用** `loopback_users.guest = false`。
3. **凭据在三个位置保持一致**：broker 的 `RABBITMQ_DEFAULT_USER/PASS`、
   服务编排的环境变量、各服务 `application.yml`。
   全部写成**可被环境变量覆盖、并带本地开发默认值**的形式
   （`${RABBITMQ_PASSWORD:-hirehub123}`），与既有 `${NACOS_PASSWORD:nacos}` 体例一致；
   本地默认值不涉及任何真实密钥。
4. **服务仍通过 `host.docker.internal:5672` 访问**（compose 已发布端口），
   不改成服务名互访：两个 compose 文件属于不同 project，默认不在同一网络里，服务名解析不可靠。

### 理由

- **一份编排 = 一条命令起全栈**：换机器/新同学接入不再需要"再装一个原生 RabbitMQ"这一步，
  环境差异从"两套部署形态"降到"一套"。
- **guest 的 loopback 限制是安全默认值，不该被绕过**：它在二期"没炸"只是因为 broker 恰好在宿主机，
  服务连接落在 loopback —— 是**部署形态的巧合**，不是配置正确。放开 guest 等于把这个保护永久拆掉。
- **凭据三处一致**（而不是只改 broker）：二期那条"服务侧无需改配置"的注释正是被证伪的假设（#33），
  所以这次显式写全，让 IDEA 直连容器 broker 的路径也能用。

### 代价与风险

- **凭据需要在多处保持同步**：broker / 服务编排 / 各服务 yml。
  缓解：统一用同一对变量名，默认值只有一处语义，改的时候一起改。
- **切账号必须先删数据卷**，否则新账号不会被创建（#34）。这意味着**broker 上的队列会被清空**；
  本项目可接受：拓扑全部在代码里声明，服务启动即重建队列。
  副作用是**切换瞬间已排定的延迟消息（面试提醒）会丢失**，
  由 `InterviewReminderScanner` 兜底扫描 + `schedule()` 的 `stillValid` 守卫补偿。
- **本地默认密码写在仓库里**：仅限本地开发（与 `root/root`、`minioadmin/minioadmin` 同级），
  生产必须由环境变量注入。

## D-37 测试策略：单测管边界，脚本管链路

### 背景

本项目相当长时间内**一个单元测试都没有**（`src/test` 为空），全部验证靠 5 个 PowerShell 端到端脚本。

这套脚本确实抓到了真问题（缓存锁导致误报 404、Q-08 的联动、RabbitMQ `guest` 跨容器登录），
但它有两个天然短板：

1. **跑得慢且依赖整套环境**（14 个容器 + 造数据 + TTL 真等待），因此不可能为"每一条非法状态迁移"都写断言；
2. **边界覆盖差**：状态机的价值恰恰在"哪些组合不允许"，而端到端只走主链路。

### 决策

1. **单元测试只覆盖「纯逻辑 + 边界」**，范围明确限定为：
   - 两个状态机（投递 D-27 / 面试 D-28）的**全部合法迁移 + 全部终态 + 事件级角色规则 + 校验顺序**
   - `JwtUtil` 的三条安全约定：refresh 不带 roles / 签名与有效期真的校验 / 无 `typ` 的历史 token 按 access 兼容
   - `CreditCodeUtil`：GB 32100 是**真算法**，编造的代码必须被挡住
   - `MockCompanyVerifier`：**"信用代码错" ≠ "企业已注销"** 是两条分支，不能混（混了会误下线岗位）
   - `JobCacheService`：**回归钉** —— 缓存被写侧清掉且抢不到重建锁时，必须落 DB 兜底，不得返回 `null`
2. **端到端脚本继续负责跨服务链路**：MQ 最终一致性、ES 同步、WebSocket、跨服务隐私、Q-08 联动。
   单测**不重复**这些。
3. **明确不做**：`@SpringBootTest` 上下文测试与 Testcontainers 集成测试 —— 既慢又要拉起中间件，
   与已有脚本覆盖面高度重叠，投入产出比低。
4. `mvn test` 必须**显式指定 `maven-surefire-plugin` 3.x**（见"代价与风险"）。

### 理由

- 单测与脚本是**互补而非替代**：脚本证明"整条链路在真实中间件下能跑通"，
  单测证明"每条边界规则单独成立、且将来不会退化"。
- 缓存那个 bug 就是最好的例子：脚本发现了它，但**依赖 30 秒锁窗口，偶然性很大**；
  单测把它变成**必然复现**，以后谁改坏都会当场红。
- 只测纯逻辑 = **零环境依赖**，`mvn test` 几秒出结果，才可能进入日常开发循环。

### 代价与风险

- **不为覆盖率而覆盖率**：单测刻意保持"少而准"。给 getter/setter 写断言是负资产。
- **必须显式钉 surefire 3.x** ⚠️：本项目未继承 `spring-boot-starter-parent`，插件版本不被管理；
  Maven 默认绑定 surefire 2.x，**它不认识 JUnit 5**，结果是**一个用例都不跑却报 `BUILD SUCCESS`**
  （输出 `Tests run: 0`）。这是最危险的一种假绿 —— 与踩坑 #30「healthy 但其实没在服务」同一类。
- **Mock 的局限**：mock 只能证明"按我 mock 的假设成立"，验证不了真实 SQL / Redis 行为。
  这部分仍由端到端脚本兜底。

## D-38 延迟任务改用 Redis ZSet（修订 D-32）

### 背景

D-32 用 RabbitMQ 的「**消息级 TTL** + DLX」做面试提醒的延迟队列，并明确不装延迟插件。

实测发现消息级 TTL 有一个绕不开的缺陷：**RabbitMQ 只在消息到达队头时才检查它是否过期。**
一条「1 天后提醒」排在队头，它后面那条「30 分钟后提醒」就得干等到队头过期 —— 最坏推迟数天。
踩坑记录 #43 有完整证据（队头 `expiration` = 48 小时；目标消息 60 秒；70 秒后队列纹丝不动）。

当初为这个缺陷配了「兜底扫描」，结果是：**扫描一直在替它兜底，而这件事没有任何告警** ——
延迟消息机制**实际上是失效的**，而脚本还会因为执行顺序不同而时绿时红。

### 决策

**延迟触发改用 Redis ZSet**，不再用 RabbitMQ 消息级 TTL：

- ZSet `hirehub:delay:interview-remind`：member = `{interviewId}:{tier}`，score = 到点毫秒
- 载荷放 Hash `hirehub:delay:interview-remind:payload`：member → JSON
- `InterviewReminderPoller` 每 1 秒取 `ZRANGEBYSCORE ≤ now` 的项，用 **`ZREM` 的返回值认领**
  （删到 1 条才算抢到，多实例天然只出一个）
- **改期 = 同一个 member 再 `ZADD` 一次**（score 覆盖，不需要知道旧 token）；**取消 = `ZREM` + `HDEL`**
- 删除 `hirehub.interview.remind.delay` 与 `hirehub.interview.remind` 两个队列、对应消费者与常量

**兜底扫描保留**（`InterviewReminderScanner`，5 分钟一轮），但它兜的已经不是队头阻塞，而是
「认领后崩溃 / 排布失败 / 服务停机期间到点」这类**任何主路径都免不了**的情况。

### 理由

- **ZSet 按 score 排序，谁到点谁先出**，不存在队头阻塞。
- **Redis 本来就在运维清单里**（缓存、分布式锁、WebSocket Pub/Sub 都在用），**不引入新组件** ——
  这比装 `rabbitmq_delayed_message_exchange` 插件更符合 D-32 的取舍。
- 相比「干脆只留定时扫描」的方案：主路径仍是**秒级**的；5 分钟粒度对"提醒"太粗，不适合当主路径，
  只适合当安全网。
- **面试可讲度**：「为什么不用 MQ 的延迟消息」是个能展开的问题 ——
  从队头阻塞讲到更普遍的「**兜底机制会掩盖主路径故障**」。

### 代价与风险

- interview 服务**新增 `spring-boot-starter-data-redis`** 依赖与 Redis 配置（此前不依赖 Redis）。
- **认领后崩溃会丢掉一条延迟项**：那时提醒行仍是 PENDING，交给兜底扫描补。
  宁可让兜底扫，也不要因为把「至少一次」实现成「至少两次」而**重复提醒用户**。
- **Redis 单点挂了主路径就停**（依赖原子 `ZREM` 认领）；此时兜底扫描仍能工作（它只依赖 MySQL）。
- 轮询间隔默认 1 秒，可配 `hirehub.interview.delay.poll-interval-ms`。

## D-39 安全加固：密码强度 + 登录失败锁定 + 越权/脱敏断言

### 背景

收官阶段做了一次安全自查，**先看现状再决定做什么**，结论分两半：

**已经达标的（不动）**：BCrypt 存密码（注册/初始化 `encode`、登录 `matches`）、网关统一鉴权、
管理端 `@PreAuthorize("hasRole('PLATFORM_ADMIN')")`、归属校验（resume/company `requireOwner`、面试 `determineActor`）、
隐私模型（未同意返 null + 屏蔽优先 + 留痕）、审计 + traceId、网关 Sentinel 限流。

**真缺口**：

1. **登录失败无任何限制** —— 可以无限撞库；
2. **密码无强度要求** —— `RegisterRequest.password` 只有 `@NotBlank`，能注册密码 `1`；
3. **横向越权与日志脱敏没有任何断言** —— 代码当下是对的，但**没有东西钉住它**（与 D-37 同一思路）。

### 决策

**只做与"生产前提"无关的那部分**（即代码质量问题）；需要公网/证书/通道的一律不做。

1. **密码强度**：注册 DTO 加 `@Size(8,32)` + `@Pattern`（必须同时含字母与数字）。
   - **为什么放 DTO 而不是 Service**：注册是唯一写密码的入口，DTO 校验覆盖所有调用方，
     将来不会被某个"内部开通账号"的路径绕过去。
2. **登录失败锁定**：新增 `LoginAttemptGuard`（Redis 计数），默认**连续 5 次锁 15 分钟**。
   - **锁定期内即使密码正确也拒绝** —— 否则爆破方只要在窗口里撞对一次就绕过了整套防护；
   - **用户名不存在也计数** —— 否则"账号是否存在"会从响应差异里泄漏出去；
   - **为什么网关限流替代不了它**：Sentinel 挡的是"每秒请求数"，而撞库是**慢速**的
     （每秒一两次，一天也能试几万次），只有**按账号**计数才拦得住。
3. **把"当前正确"变成"可执行判据"**：新增 `scripts/phase3f-verify.ps1` ——
   密码强度、登录锁定、横向越权、日志脱敏四组断言。
4. **明确不做**：HTTPS/WAF、KMS、DDoS 防护、图形验证码/短信验证（本地无公网入口、无短信通道）。
   这些服务的是"给真实用户用的环境"的前提，与本地演示/简历项目无关（见 README 的说明）。

### 代价与风险

- **测试密码约定从 `123456` 改为 `123456ab`**（否则新策略下所有脚本注册失败），7 个脚本已同步。
  ⚠️ **用旧密码创建的既有账号（`alice` / `bob` 那批）在新脚本下登不进去** ——
  验证请用 `-Fresh` 模式（README 也正是这么写的）。
- **账号级锁定天然带来"拒绝服务式锁定"**：攻击者可以故意用别人的用户名去撞，
  把该账号锁住。这是所有"按账号计数"方案的共性代价（缓解手段是按 IP+账号双维度计数、
  或指数退避）；本项目为本地演示，不引入这层复杂度，但**这一点必须知道**。
- 锁定 key 用 `auth:login:lock:{username}`，TTL 到期自动消失，不长期堆积。
- 日志脱敏只做了"断言"（保证现在没打），**没有做主动脱敏组件** ——
  因为项目本来就没把手机号/身份证写进日志；断言的意义是"以后有人加了能当场发现"。
